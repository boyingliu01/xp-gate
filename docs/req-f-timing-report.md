## 测量方法

审计日志的每一行是"某门禁某次运行"。还原为"一次 hook 运行"需要两步：

1. **按时间聚类**：同一 hook 运行的门禁行在几分钟内连续写入。
2. **按序列重启切分**：`version-consistency` 永远是每次运行的第一行，出现它即表示新一次运行开始。不做这一步会把连续两次提交合并成一次（实测 14 行、26.0s 的窗口其实是两次运行）。

只保留产生 6–14 个门禁行、且无异常时长（≤120s）的干净运行——这排除了门禁拒绝后重试的叠加，那些记录的"总和"是 792s、241s 这类无意义数字。

## 诚实披露

### 1. 前 15 个提交跑的是旧 hook

`core.hooksPath` 指向 `~/.config/xp-gate/hooks/`。`audit-sanitize.sh`、`ccn-ratchet.sh`、`docs-only.sh` 三个新库在已安装副本里**根本不存在**，直到执行 `xp-gate doctor --sync-hooks` 才同步。

所以：`a30af53b`（REQ-B sanitizer）落地后，后续提交仍在写 `duration_ms: 1792337852793`；docs-only 短路在提交侧从未生效。

**这是"为什么日志里长期是脏数据"的直接原因**，已记录在 `.sprint-state/phase-outputs/phase-3-summary.md`。

### 2. 6 个样本仍然偏少

n=6 不足以做显著性检验。但这次不只有"总数变快"这一个论据——**每个门禁的绝对值都在正确的位置上**（纯 docs 提交的 tsc 是 672/902ms = 跳过，而不是 11s = 运行）。这是机制层面的证据，不是统计层面的。

### 3. 手测的 3 文件代码提交是 80.0s

高于 p50 27.5s，也高于 sprint 前的 p50 69.4s。原因可查：那次改动动了 `src/npm-package/` 下 3 个文件，`architecture-boy-scout` 单项跑了 24s（该门禁对跨目录改动最敏感），另有 `build-integrity` 11.2s。

**代码提交本来就不走短路**——F2 只对 docs 提交生效。所以 80.0s 既不能证明也不能否定提速，它是**代码提交的当前真实成本**。要降低它需要另一条路径（例如 `architecture-boy-scout` 的增量分析），不在本 sprint 范围。

### 4. 无效数据已剔除

- `iac-security` 的 "58739ms"：sprint 后只有 1 个样本，是噪声。
- `tests-coverage` 的 p50 波动：真实分布在 288ms–27s 之间，取决于增量选中的测试量，不是性能退化。
- 未切分序列重启时算出的 "n=1, −67.7%"：样本提取错误，已修正为 n=6。

## 结论

REQ-F **达成**。三条改动都有独立可归因的证据，短路机制在门禁层面被直接观测到（tsc 672ms 而非 11s）。`n=6` 的样本量是已知局限，已如实标注；但这不影响"短路已生效、重门禁成本降到接近零"这一机制性结论。
