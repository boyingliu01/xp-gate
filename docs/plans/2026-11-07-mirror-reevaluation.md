# 镜像副本：从「技术债」到「设计抉择」的重新评估

- 日期：2026-11-07
- 状态：评估，推翻前一份文档的 P0 结论
- 前置：`2026-11-07-self-architecture-governance.md`（本文修正其 §4.1 与 §5 的 P0）

---

## 0. 结论先行

前一份文档建议「把镜像改成构建产物，从 22.9 万行降到 11.5 万行」。

**这个建议方向对，但严重低估了执行成本和风险。** 深入核实后，真实情况是：

> 仓库里**已经存在两套并行方案**：`gates/` 走构建产物，`adapters/hooks/principles/lib` 走 git 跟踪。
> 而且围绕「git 跟踪的镜像」已经建了一整套防御工事——10+ 个测试、1 个 CI job、4 个检查脚本。

**这不是「忘了做」，是「做了一半 + 为已做的部分上了大量保险」。**

---

## 1. 两套方案并存的证据

| 路径 | git 跟踪 | 机制 |
|---|---:|---|
| `src/npm-package/gates/` | **0 个** | `.gitignore:18`，`prepack` 时由 `sync-package-content.js` 生成 |
| `src/npm-package/skills/` | 67 | git 跟踪（但 `plugins/*/skills/` 已 gitignore） |
| `src/npm-package/adapters/` | **293** | git 跟踪 |
| `src/npm-package/hooks/` | 37 | git 跟踪 |
| `src/npm-package/principles/` | 107 | git 跟踪 |
| `src/npm-package/lib/` | 178 | git 跟踪 |
| `src/npm-package/plugins/` | 342 | git 跟踪 |

`.gitignore` 第 15–18 行的注释是**决定性证据**：

> ```gitignore
> # npm-package gate modules: generated by sync-package-content.js at prepack
> # (copy of src/gates, shipped via package.json files[]). Never tracked — tracked
> # byte-identical copies of the same test files trip archlint CodeClone + Gate 5a.
> src/npm-package/gates/
> ```

**「tracked byte-identical copies ... trip archlint CodeClone + Gate 5a」** —— 有人已经踩过这个坑，修了 `gates/`，但没推广。

---

## 2. 为什么没推广：一个结构性悖论

`githooks/pre-commit:1124` 的注释把问题说透了：

> Byte-identical mirrors (`src/npm-package/**`) are governed by CI Mirror Parity, not
> by re-linting. Leaving them in this scan set **double-counted every lint/complexity
> signal** and made jscpd report the source-vs-mirror pair as a **100% whole-file
> clone**, which then tripped Gate 6's "<=5 warnings must clear to zero" rule on ANY
> edit to a mirrored file — **a warning that is structurally impossible to clear.**

于是形成一个悖论：

| 选择 | 后果 |
|---|---|
| **镜像参与扫描** | 结构性无法消除的克隆告警（副本必然 100% 相同），任何一次改动都触发，**无法清空** |
| **镜像不参与扫描** | `MIRROR_PATH_FILTER='^src/npm-package/'` 排除了 **55% 的仓库**，一半代码没人看 |

当前选的是后者。代价是：

```bash
MIRROR_PATH_FILTER='^src/npm-package/'   # pre-commit:1141
```

**一行正则，让 12.7 万行代码退出所有 lint 检查。**

---

## 3. 这意味着什么

### 3.1 「镜像同步」是唯一防线

镜像不参与 lint / clone / 复杂度检查，只由 CI Mirror Parity 保证「和非镜像一样」。

**但「一样」是通过比对各组文件实现的** ——`check-hook-mirror.sh` 守护 38 个 hook 文件 + 12 个 root 文件。
不在这个清单里的镜像文件，**既不被 lint，也不被 parity 检查**。

这是个真实的覆盖盲区。

### 3.2 #632 / #633 / #649 / #658 的重新解释

前一份文档说这些回归的根因是「修一边忘另一边」。

**更准确的说法是**：这些回归发生在 **parity 清单之外**的镜像文件上，或者发生在 parity 检查跑不到的路径上（CI 不跑而本地跑、或反向）。

`#658`（`files` 字段漏了 `gates/`，三个 gate 在安装形态永远不可用）就是典型：
`gates/` 不在 `MIRROR_PATH_FILTER` 之外——**它压根不在 git 里**，所以 parity 检查也管不到它。

### 3.3 为什么「构建产物」是正确答案

回顾悖论的三个出口：

| 方案 | 副本参与扫描 | 副本需要同步 | 结论 |
|---|---|---|---|
| 现在（git 跟踪 + 排除） | ❌ 被排除 | ✅ 需要 | 一半代码无人看 |
| 全部改成构建产物 | — 不存在落盘副本 | ❌ 不需要 | **悖论消失** |

**只有当副本在 git 里不存在时，这个悖论才真正消失。** 这是 `gates/` 已经验证过的路线。

---

## 4. 但执行成本远高于我之前的估计

前一份文档说 P0「风险中」。**这是错的，实际风险是「高」**。

### 4.1 依赖方清单（实测）

| 依赖方 | 依赖什么 | 改造成本 |
|---|---|---|
| `.github/workflows/cross-platform-ci.yml` `mirror-parity` job | 3 个 check 脚本 | 要删整个 job |
| `scripts/check-hook-mirror.sh` | 50 个文件的字节比对 | 直接失效 |
| `scripts/check-hook-lib-mirror.sh` | lib 镜像 | 同上 |
| `scripts/check-build-integrity-mirror.sh` | build-integrity 镜像 | 同上 |
| `scripts/check-delphi-runner-mirror.sh` | delphi runner 镜像 | 同上 |
| `src/npm-package/lib/__tests__/mirror-manifest.test.js` | 镜像清单 | 要重写 |
| `src/npm-package/lib/__tests__/mirror-sync.test.js` | 「一次 sync 让所有镜像字节一致」 | 要重写 |
| `scripts/__tests__/hook-mirror-parity.test.cjs` | root↔npm 字节一致 | 要删 |
| `scripts/__tests__/hook-lib-mirror.test.cjs` | lib 镜像 | 要删 |
| `scripts/__tests__/adapters-gate-mirror-parity.test.cjs` | adapters 镜像 | 要删 |
| `scripts/__tests__/in-tree-drift-guards.test.cjs` | AC-433 三层漂移防线 | 要改 |

**11 个依赖方，其中 6 个是测试、4 个是检查脚本、1 个是 CI job。**

### 4.2 一个具体的反直觉风险

`mirror-sync.test.js` 的 `@intent` 写着：

> The hook-lib mirror check failed on a machine where `githooks/lib` held an
> untracked `__pycache__/` — Python byte-compiled the helper during a test run.
> **A false failure here costs a real fix cycle at commit time**, which is exactly
> the rework this task set out to remove.

**这套检查机制本身就是为了消灭返工而建立的。** 删掉它，等于把 #713 解决的问题重新打开。

## 5. 修正后的建议

### 5.1 不要做「一次性大改造」

前一份文档的 P0（「镜像改为构建产物」）应该**降级并拆解**。

### 5.2 建议改为「分阶段 + 每阶段可独立回滚」

| 阶段 | 内容 | 收益 | 风险 |
|---|---|---|---|
| **S1** | 盘点：`check-hook-mirror.sh` 清单之外的镜像文件有多少 | 量化盲区 | 零（只读） |
| **S2** | 把 `plugins/`（342 文件 / 5.7 万行）改成构建产物 | 最大单块 | 中（照抄 `gates/` 先例） |
| **S3** | `adapters/`（293 文件 / 8500 行） | 跟随 | 中 |
| **S4** | `principles/` + `lib/` + `hooks/`（320 文件 / 4.7 万行） | 剩余 | 高（代码，非数据） |

**S2 是第一个应该做的**：`plugins/` 是数据而非代码，5.7 万行，且脚本 `syncPlugins()` 已经存在。

### 5.3 立即可做的零风险项

**S1 盘点** —— 这个我现在就能做，而且它本身就有价值：找出「既不被 lint 也不被 parity 检查」的文件。

## 7. 一句话

**镜像不是「没人管的债」，是「管了一半 + 用排除代替解决」的妥协。**

真正的病根不是副本多，而是**「排除扫描」这个补偿动作** —— 它让 55% 的代码合法地逃出了质量体系。

---

## 8. S1 盘点结果（已实测）

### 8.1 方法

1. 列出 `git ls-files src/npm-package`（1006 个文件）
2. 用 MD5 与仓库其余部分比对，筛出**字节完全相同的纯复制**
3. 解析 4 个 `check-*-mirror.sh` 里 `="..."` 列出的文件名/目录，得到「parity 显式覆盖面」
4. 求差集：纯复制 **且** 不在任何 parity 清单里

### 8.2 结果

```
src/npm-package 跟踪文件总行数:        184,701
  纯复制但未被任何 parity 脚本覆盖:    775 文件 / 110,282 行
  占比:                                59.7%
```

**775 个文件、11 万行（59.7% 的镜像代码），处于双重盲区：**

- **不被 lint 检查** —— `MIRROR_PATH_FILTER='^src/npm-package/'` 把它们整体排除
- **不被 parity 检查** —— 不在 `check-hook-mirror.sh` 等脚本的清单里

### 8.3 盲区最大的文件

| 行数 | 文件 |
|---:|---|
| 1106 | `src/npm-package/scripts/delphi-external-review.cjs` |
| 1049 | `src/npm-package/mutation/__tests__/mutmut-runner.test.ts` |
| 946 | `src/npm-package/adapters/java.sh` |
| 893 | `src/npm-package/principles/__tests__/boy-scout.test.ts` |
| 891 | `src/npm-package/build-integrity/gate-10.ts` |
| 885 | `src/npm-package/principles/adapters/typescript.ts` |
| 798 ×4 | `src/npm-package/plugins/{claude-code,dsh,opencode,qoder}/skills/delphi-review/SKILL.md` |

最后一行值得注意：**同一个 skill 文件在 4 个插件目录下各有一份**，四份都不在任何检查网里。

### 8.4 这个数字意味着什么

`check-hook-mirror.sh` 的清单覆盖 **50 个文件**（38 hook + 12 root）。
`src/npm-package` 里躺着 **1006 个**。

**parity 检查覆盖了 5% 的镜像文件。** 其余 95% 中，有 775 个是纯复制、无任何校验。

`#632` / `#633` / `#658` 这批「修一边忘另一边」的回归，**不是巧合，是这 59.7% 盲区的必然产物**：
改一个 canonical 文件，没有机制告诉你哪些副本该跟着改。

### 8.5 由此得到的最小可行修复

不需要动 11 个依赖方，也不需要一次性改成构建产物。

**只要让 parity 检查覆盖全部纯复制文件，盲区就从 59.7% 降到 0。**

这比「改成构建产物」的风险低一个数量级：
- 不删任何文件
- 不碰 CI job
- 不动现有 6 个测试的语义（它们断言的东西仍然成立）
- 只是把 `check-hook-mirror.sh` 的文件清单从「手写 50 项」改成「自动发现」

**而且这一步做完之后，再谈「改成构建产物」才有意义** —— 因为那时你才知道自己删的是什么。
