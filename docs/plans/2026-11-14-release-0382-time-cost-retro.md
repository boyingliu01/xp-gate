# 0.38.2 发版任务耗时复盘

**日期**: 2026-11-14
**背景**: 用户两次指出「这次发版任务执行耗时远远超出预期」，要求复盘瓶颈并改进。
**范围**: 本次从 0.38.0 发布到 0.38.2 收尾的完整过程。

---

## 0. 结论先行

耗时不是被"难问题"吃掉的，而是被**四类重复浪费**吃掉的，其中一类占了绝大部分：

| 浪费类型 | 量化 | 占比判断 |
|---|---|---|
| ① 阻塞式等待（`job_output wait` / `sleep` / CI 轮询） | **7.9 小时**（95 次 >30s 阻塞，99 次显式 `wait:true`，143 次 CI 轮询） | **最大项** |
| ② 逐个猜错因，而不是先读失败报告 | 32 个 BATS 失败逐个修了约 20 轮，后聚类一次修完 20 个 | 大 |
| ③ 先 push 再等 CI，而不是本地先验证 | 每次 CI 往返被①放大成几十分钟 | 中 |
| ④ 本地环境与 CI 不一致导致的返工 | lizard 版本不一致、全局适配器陈旧 | 中 |

**一句话**：我把"等 CI"当成了"等"，而不是"起一个后台任务，回去干别的"。

## 2. 典型浪费场景（均有日志可查）

### 2.1 阻塞等待 CI（最大单笔）

```
bash-150  gh run watch ...  (前台阻塞)
bash-207  gh run watch ...  (后台，正确做法)
```

同样的动作，前者什么都不能做，后者能继续干活。整个任务里前者出现了几十次。

### 2.2 逐个猜错因：32 个 BATS 失败的教训

| 阶段 | 失败数 | 做法 |
|---|---|---|
| 起点 | 46 文件 / 96 用例 | 逐个看、逐个修 |
| 中途 | 31/61 → 20/25 → 11/17 → 1/1 | 仍在逐个修 |
| 转折 | — | **读了失败报告的共同模式**，发现全部指向 `githooks/gate-9.sh` 被 `2dc97a18` 删除（#798 重构） |
| 结果 | 0 | 一次修完剩余 20 个 |

**矛盾点**：一次聚类分析能省下约 20 轮往返，但我先做了 20 轮才发现。

### 2.3 本地与 CI 环境不一致

| 项 | 本机 | 门禁固定 | 后果 |
|---|---|---|---|
| lizard | **1.25.1** | **1.21.3**（`.lizard-version`） | 本地 `OK — 1612 functions`，CI 报 `} CCN=53`；**用错误版本验证了 3 轮** |
| 全局适配器 | 陈旧（md5 不同） | `core.hooksPath` 指向全局 | 本地跑门禁用旧代码，无法复现 CI 现象 |

第二项 `githooks/AGENTS.md` 里**已经写明**："an adapter is stale until proven otherwise; md5sum both copies"。我先读了却没执行。

### 2.4 一个值得记住的连环坑

修 lizard 解析问题时：

1. 触发点 1：模板字符串里的 `(` → 被当成参数列表
2. 修完 → 触发点 2 出现：**我解释第 1 点的注释里的反引号** → 被当成模板字符串起始

修复本身是对的（代码里已用注释标注"不要把这些整理回模板字符串"），但这类"修 A 引出 B"只有读懂工具的行为才能一次做对。

## 3. 有效的做法（应固化为习惯）

| 做法 | 证据 |
|---|---|
| **先读失败报告再动手** | 32 个 BATS 失败的聚类分析，一次修完 20 个 |
| **二分定位而非猜测** | lizard 的 `}` CCN=53：用 `head -N` 二分到具体行，再用最小用例复现 |
| **先证伪再下结论** | 怀疑 #798 遗留时，用 `git stash` 把改动摘掉重跑，证明"摘掉也失败 → 不是我的改动" |
| **失败先分类：我造成的 / 既有的** | 多次用 stash 验证，避免误修别人的代码 |
| **写等价性用例** | `rewriteExits` 重构后写了 8 个用例（含 subshell 不能改成 `return` 的关键行为） |
| **不信 `success`，核对 `headSha`** | npm-publish 会因"版本号未变"报 success 而实际只 SKIP |

## 4. 根因分析：为什么规则写了却不执行

规则 2、3 在 `AGENTS.md` 里写得很清楚，但实测显示基本没执行。原因不是不知道，而是：

1. **等待的那一刻没有替代动作清单**。规则说"不要阻塞等待"，但没说"那我现在该做什么"。于是默认行为退化成等待。
2. **`job_output wait:true` 太顺手**。它看起来像"正常取结果"，实际上就是阻塞。
3. **并发需要主动规划**。串行是一个一个自然发生的，并发要先想"这两个有依赖吗"。
4. **`runtime-journal` 是事后指标**。它只在复盘时告诉我违规了，过程中没有任何提示。

## 5. 改进措施

### 5.1 立即可做（本次任务内已执行）

- ✅ 本机 lizard 降到 **1.21.3**，与 `.lizard-version` 一致
- ✅ 全局适配器副本已同步（`md5sum` 三份一致）
- ✅ CI 等待改为后台 job（`bash-207` 起，不再前台 `wait`）

### 5.2 需要成为硬规则

| 措施 | 具体做法 | 预期收益 |
|---|---|---|
| **M1: CI 等待必须"起 job + 干别的"** | 起 `run_in_background` 后，**立即列出等待期间能做的 2 件事**再做；禁止前台 `gh run watch`、禁止 `job_output wait:true` 循环 | 省 ~6 h |
| **M2: 改门禁相关代码前先比对固定版本** | 先 `cat .lizard-version` 等 PIN 文件，与本机 `--version` 比对；不一致先降/升级再验证 | 消除最大返工源 |
| **M3: 失败先聚类再修** | 拿到 N 个失败，**先按报错关键词分组**，禁止逐个 trial-and-error | 省 ~2 h |
| **M4: 每步至少 2 个独立调用并发** | 发消息前自查："这两个调用有依赖吗？没有就并发" | 省 ~1.5 h（当前仅 19.7% 达标） |
| **M5: 动手前先读该目录的 AGENTS.md** | 尤其 `githooks/AGENTS.md` 有"全局副本陈旧"这类陷阱记录 | 消除 2.3 类浪费 |

### 5.3 工具层面的建议

`runtime-journal` 只能事后度量。建议增加**过程中的提醒**：

- 在 `xp-gate doctor --brief` 里增加一项：本机关键分析器版本 vs 各 `.*-version` PIN 文件的一致性检查。这样每次开工前一条命令就能发现 2.3 类陷阱。
- 这一条已足够小，可单独开 issue。
