# xp-gate 开发速度诊断与提效计划（0.32.2 复核）

**日期**: 2026-10-30
**触发**: 用户怀疑"工具调用次数太多"是主因，要求一次不预设结论的全面诊断。
**结论**: 调用次数多是**症状**，不是**主因**。真正的乘法项是**返工率（47.6%）**，其次是**串行门禁电池**与**不批量调用**。旧诊断（#653）"门禁只占 1%"是分母被污染造成的误判——复核见 §1。

---

## 0. 数据与方法

| 源 | 规模 |
|---|---|
| `.dsh/sessions/--D-projects-xp-gate--/*`（26 会话） | 解压后 1.2 亿字符，24,878 次工具调用，24,303 个 step |
| `.xp-gate/audit.jsonl` | 8,179 条 xp-gate 门禁执行记录（608 个唯一 commit） |
| git 历史 | 近 60 天 680 个提交，近 45 天 679 个 |

分析脚本：`.agent-tmp/session-analysis/task2-*.cjs`（可复跑）。

### 两个必须先拆掉的"假数据"

原始 `call→result` 时间差**不能直接累加**，否则得到天文数字。实测两个污染源：

1. **resume/日志落盘间隔**：单次 `pwsh` 调用记录的时长为 **78.0 小时**。逐事件核对——调用发生在 `2026-10-23T10:34Z`，而对应的 `tool/result` 直到 `2026-10-26T16:33Z` 的一个 `compaction/prune` 才被写进日志。它测的是"用户走开 + 日志冲刷"，不是命令耗时。全库共 **368 次**这类被冲刷的间隔，累计 **653.6 小时**。
2. **`duration_ms` 写入 epoch 时间戳**：`audit.jsonl` 里 **397/8179（4.9%）** 条 `duration_ms` 约 `1.79e12`（≈56 年），全部来自 gate-1(191) 与 gate-11(206)。同一字段偶尔装的是"时间点"而非"时长"。

把这两类剔除/裁剪后，总账才成立。下文所有数字都基于"去假数据"后的口径。

## 1. 复核 #653："门禁只占 1%" 是错的

旧诊断的分母是 **803 小时工具时长**（= 22,149 次调用的原始时长求和）。那 803 小时里绝大部分就是上面说的 78 小时级 resume 间隔。用它当分母，任何真实耗时都显得"只占 1%"。

去假后的正确剖面：

| 口径 | 数值 |
|---|---|
| 有效计时（去 resume 间隔、门禁 `duration_ms` 剔除 epoch 值并封顶 10min） | **251.7 h** |
| 其中 模型延迟（result→下次 call） | 105.7 h（42%） |
| 其中 工具延迟（call→result） | 146.0 h（58%） |
| **门禁实际耗时**（8,179 次执行，清洁口径求和） | **87.5 h ≈ 34.8%** |

**门禁不是 1%，是约 35%。**这是本次诊断与旧结论最大的分歧，也是为什么必须重做。

### 2.2 Shell 命令里到底在干什么（pwsh+bash，15,730 次）

| 类型 | 次数 | 占比 |
|---|---|---|
| 纯读取/搜索（`Get-Content`/`Select-String`/`Get-ChildItem`/`cat`/`grep`…，且不含执行动作） | **5,144** | **32.7%** |

## 3. 真正的乘法项：返工

| 指标 | 值 |
|---|---|
| 近 45 天提交 | 679 |
| 其中 `fix`/`revert` | **323（47.6%）** |
| 高频 fix 域 | gates 19、doctor 18、delphi 18、principles 14、githooks 13、complexity 13、pre-push 12、hooks 12、ci 12、gate-5 10 |

**近一半提交是在修已经合进去的东西。**每个 fix 都要重新付一次 3.8 分钟的门禁电池、重新起一批工具调用。47.6% 的返工，对总耗时是**乘法**（同样的意图被验证 2–3 遍），而不是加法。这才是"慢"的主因——不是模型慢，也不是某个 gate 慢，而是**验证发生在错误的时间**：先写完、先提交、被门禁打回、再改、再提交。

这与 #652 的观察一致，也解释了为什么 skills 里 `CCN`/`jscpd`/`archlint`/`mirror` 出现 **0 次**：BUILD 阶段根本不知道门禁红线，于是 27% 的门禁失败本可以避免。

### 3.1 另外：串行 + 不批量

- 门禁除审计写日志外**几乎全串行**（pre-commit 里唯一 `&` 是 record_gate_audit）。
- **1.03 calls/step；仅 2.7% 的 step 并行 ≥2 个调用**（24,187 个调用 step 里只有 641 个批量化）。也就是每次工具调用都要单独付一次 15.3 s 的模型往返。

## 4. 归因排序（按可回收小时数）

| # | 根因 | 机制 | 可回收（估） | 类型 |
|---|---|---|---|---|
| 1 | **返工率 47.6%** | 验证滞后 → 同一意图重跑门禁 2–3 次 | ~55–65 h | 乘法 |
| 2 | **不批量调用**（1.03/step） | 每次调用付 15.3 s 模型往返 | ~50–59 h | 线性×次数 |
| 3 | **32.7% shell 在读取/搜索** | pwsh 往返 10–30 s，本可 read/grep/glob 毫秒级 | ~25–30 h | 线性×次数 |
| 4 | **门禁串行** | 电池 3.8 min 中可并行部分未并行 | ~15–20 h | 线性×提交数 |
| 5 | **遥测失真**（4.9% epoch、402 条 >10min） | 看不到真实剖面，优化无的放矢 | 间接 | 使能项 |

> #1 与 #2/#3 有重叠：批量化和少返工会同时减少调用次数。"工具调用次数太多"是这三件事的**共同表现**，不是独立病因。

## 5. 提效计划（按 ROI 排序，每步可独立验收）

### P0 — 修遥测（先让数据可信，半周）

1. **`duration_ms` 类型归一**：审计写入端校验必须是非负整数且 `< 1 天`；发现 epoch 值（`>= 1e12`）写 `duration_anomaly` 并对该 gate 记 WARN，不要再把它当合法时长入库。补一条回归测试锁死（当前 397 条会直接红）。
   - 验收：`audit.jsonl` 重算后 gate-1/gate-11 不再有 >1e12 的 `duration_ms`。
2. **`xp-gate audit --stats` 增加健康度**：输出"异常时长条数 / 占比"，异常 >0 时 CI 失败。
   - 验收：`xp-gate audit --stats --json` 含 `anomalies` 字段；异常时退出码非 0。

### P1 — 削返工（最大单项，1–2 周）

3. **门禁红线前移进 BUILD skills**（直接解 #652）：把 Gate 3(CCN>5 warn/>10 block)、Gate 6 Boy Scout(新文件 0 warning、函数 ≤50 行、嵌套 ≤4)、Gate 2(jscpd >5%)、Gate 4、mirror/sync 纪律，写成 `skills/sprint-flow/references/phase-3-build.md` 的一页「提交前自检清单」，并在 ralph-loop step 0 里跑 `xp-gate check . --changed --brief`。
   - 验收：skills 文本出现上述阈值；抽查下一个 sprint 的 fix 提交占比。
4. **`xp-gate check --changed --brief`**：只跑"本次 diff 会触发的 gate"，输出一屏摘要（≤15 行），**目标 <5 s**（当前 `xp-gate check . --all` 是整棵树的电池）。
   - 验收：在本仓库一次中等改动上计时 <5 s；输出含 gate→PASS/SKIP/BLOCK 一屏。
5. **契约先测**：新功能默认先写集成/契约测试（`plugins/dsh` 已有 `contract.test.ts` 范式），让"发布流水线契约"类失败在本地就红，而不是在 CI 里用 `jq` 语法错误提示（0.32.2 的 dsh 插件正是这么漏发的）。

### P2 — 降调用次数（1 周）

6. **read/grep/glob 优先，禁止用 shell 读取**：把"文件读取/搜索一律用 read/grep/glob；shell 只用于执行"写进 `AGENTS.md` 与 BUILD skill 的硬性反模式。
   - 验收：抽样会话，`pwsh` 中纯读取占比从 32.7% 降到 <5%。
7. **强制批量**：独立调用必须在同一 step 内并发发出（工具契约已支持）。把"≥2 个独立调用必须合并到一步"写成规则。
   - 验收：calls/step 从 1.03 提到 ≥2.0。
8. **`job_output` 完成即通知**：长任务用 `run_in_background` + 完成通知，禁止 `wait:true` 轮询；`job_output` 默认短超时。当前 66.5 h 花在等后台任务上，其中 p90 单次 600 s。
   - 验收：`job_output` 调用数下降 ≥50%。

### P3 — 并行门禁（2 周，收益中等）

9. **pre-commit 门禁分组并行**：Gate 0/2/3/4/8（快、无副作用）与 Gate 1/5/6/9/10（慢）分两批并行；有写副作用的 gate（baseline 写入、mirror 生成）必须仍串行且受锁保护。
   - 验收：单次提交电池 median 从 228 s 降到 ≤150 s（本仓库 A/B）。
10. **`gate-5` 增量测试**：只跑受影响文件的测试（`vitest --changed`），全量留给 pre-push。

## 6. 预期效果（保守）

若 P0–P2 落地（不依赖 P3）：返工率减半、calls/step 提到 ~2、纯读取 shell 清零，估计总耗时下降 **40–55%**；若再加 P3 并行，**on top** 再降一档。每一条都有上面测得的基线做 A/B 对照。
