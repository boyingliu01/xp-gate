# Delphi 评审：从「二值表决」到「条目化跟踪 + 证伪冻结」

**日期**：2026-11-26
**状态**：APPROVED — R2 delphi-review 第二轮修订稿 3 轮达成 3/3 共识（100%）；三条非阻塞建议已并入 §10.1
**基线**：`main @ c562ae61`（工作分支 `refactor/orthogonal-decomposition`）
**前置约束**：本设计**不得与活跃的 CCN 重构并发落代码**。见 §7。

---

## 0. 一句话结论

**多轮迭代的成本来自"一个席位说 REQUEST_CHANGES"这个二值信号，不来自"三个视角"。**
把二值表决换成**条目化问题跟踪 + 证伪冻结**，可以在**不降低发现能力**的前提下压掉大部分轮次；
而把三席位改成同视角 2:1 投票，会**用发现能力换速度**——这正是最不该换的指标。

### 0.1 首轮评审结论与修订（2026-11-27）

第一版过 R2 delphi-review（`g-deepseek-v4-pro` / `g-qwen3.7-max` / `g-minimax-m3`），
**五轮 0/3 APPROVED**。三个席位没有反对核心方向（条目化 + 冻结替代二值表决；
保留三视角），反对的是**实施细节的三处硬伤**：

| ID | 严重度 | 问题 | 本版修订 |
|---|---|---|---|
| F-01 | critical | 内容哈希做 finding ID 不稳定；一旦漂移，冻结与释放**静默失效** | §3.1 改为「位置 + 关键词集合签名 + 编辑距离匹配」 |
| F-02 | critical | `disprove()` 由编排者自批，是自我放行的后门 | §3.3 改为证据 schema + 强制可执行命令 + 审计日志 |
| F-03 | critical | 收敛判据写「2 席 APPROVED」，与「门禁不改 0.90」**自相矛盾** | §3.5 收紧为**工具与门禁同为 3/3**，阈值不可配 |
| F-05 | major | 状态模型不完整（resolved 后能否 reopen、重复 ID 如何合并） | §3.1.3 补齐状态转换表 |
| F-04 | major | 席位释放导致同意疲劳，漏掉后续新缺陷 | §3.4 增加「新 critical 触发重新召回」 |
| F-06 | major | T6「逐字节一致」不可达 | §6 T6 改为**快照/黄金测试** + 显式兼容边界 |
| F-07 | major | S1/S2 与 CCN 重构绑定过重，方案可能长期搁置 | §7 改为**按文件所有权分阶段合并** |

> F-03 是我第一版最严重的错误：它不是一个实现细节，而是**两份互相矛盾的规则同时存在**。
> 评审把它挑出来，说明这轮评审有价值——它拦住了一个会写出门禁永远拒绝的证据的设计。

## 1. 问题与现状（实测，非推断）

### 1.1 当前机制的真实形状

| 机制 | 位置 | 现状 |
|---|---|---|
| 三视角分工 | `scripts/delphi-prompts.cjs:13-46` | architecture / technical / feasibility，各 5 个正交关注维度 |
| 共识判定 | `plugins/dsh/src/delphi.ts:280-315` | 只数 APPOVED 个数，`approvals / validCount` |
| **条目提取** | — | **不存在**。报告原文整份保存，只解析 `VERDICT` 和 `CONFIDENCE` |
| 阈值 | `delphi.ts:74-75` | 90%，且 `REQUIRED_EXPERTS = 3` → **唯一可行值就是 3/3** |
| 门禁侧硬编码 | `githooks/lib/validate-code-walkthrough.cjs:576` | `ratio < 0.90` 直接 BLOCK |
| 停止条件 | `delphi-run.ts:115` | `approvals / seats * 100 >= threshold` |

### 1.2 二值信号导致的三类无效轮次

**A 类：真问题已修，但席位不再改票。**
`parseVerdict` 只认 `APPROVED` 与 `REQUEST_CHANGES` 两档。一个席位在 Round 1 指出 5 个真问题、
后来全部修复，它下一轮仍然只会说 `REQUEST_CHANGES`。系统无法区分「还有新问题」
与「还是那批旧问题，只是没给重测材料」。

**B 类：被证伪的条目反复出现。**
`docs/adr/0004-walkthrough-at-one-third-consensus.md` §"决策点"记录：第 6 轮三条 critical
**经实测全部不成立**，第 5 轮 FC-01 同样不成立。代码里没有任何机制记录"这条已被证伪"，
所以每一轮它都会重新成为反对理由。**这是本设计最直接的收益点，且有真实的 ADR 证据。**

**C 类：席位无法验证，只能推断。**
`delphi-run.ts:48` 的 prompt 写 `Approve only if you would personally ship this`，
但输入是 **≤40 KB 的片段**（Gate MW 预算），席位没有任何可执行的验证手段。
ADR-0004 §"How to avoid this next time" 的结论原文：

> 评审输入必须是**完整文件**，不是片段。本轮六次评审里有两次（第五、六轮）的
> 不成立断言可以直接归因于片段输入。

### 1.3 关于"三视角 vs 同视角 2:1"

**反方论据（ADR-0004 实测）**：前五轮每轮都抓到真缺陷，含**两处数据丢失**
（`restorePyproject(path, false)` 在备份成功后删除用户文件、`[` 越界删掉下一行）。
这类缺陷**由单一席位、单一轮次命中**——单点发现，不需要多数同意。

**同视角 2:1 的根本缺陷**：缺陷存在**相关性**。三个模型在同一视角下会一起漏掉同一个盲区；
多数投票只能压**随机**误差，压不了**系统性**盲区。而三个正交视角的失明事件近似独立。

**结论**：视角多样性是这套机制唯一不能丢的东西。**不采用同视角 2:1 替代方案。**

**但采纳其合理的部分**：如果"阻断"被定义为**未解决的阻断条目**而不是"某个席位投了反对票"，
那么 2/3 在语义上就是可以接受的——因为那时 1/3 的反对票已经变成了具体条目，
要么被解决，要么被证伪，不会凭空消失。**本次不改门禁（用户决策），只把路铺好。**

## 3. 设计

### 3.1 核心数据结构：一条 finding

#### 3.1.1 结构

```jsonc
{
  "id": "TC-01",                 // 席位前缀 + 稳定序号；由下文的匹配器维护，不由模型指定
  "seat": "technical",           // 提出者
  "severity": "critical",        // critical | major | minor
  "title": "prepare 阶段 catch 硬编码 restorePyproject(path, false)",
  "location": "src/mutation/runners/mutmut-runner.ts",   // 归一化后的文件路径，不含行号
  "keywords": ["restorePyproject", "pyproject", "catch"], // 归一化后的关键标识符
  "fix": "写入失败时不得删除用户备份",
  "status": "open",              // open | resolved | disproved
  "evidence": {                  // 仅在 resolved/disproved 时存在（§3.3）
    "kind": "command",           // command | commit
    "command": "node -e \"...\"", // kind=command 时必填
    "output": "…",               // 实测输出（截断至 4 KB）
    "commit": "abc123"           // kind=commit 时必填
  },
  "status_changed_at_round": 1
}
```

#### 3.1.2 ID 稳定性：三要素匹配，而不是哈希（修订 F-01）

**第一版的错误**：用「标题归一化后的哈希」做 ID。标题是自然语言，中文措辞、标点、
代码片段引用的任何微小变动都会改变哈希，而哈希一变，`resolved`/`disproved` 的冻结
就静默失效——**没有任何报错，轮次只是悄悄变多**。

**本版方案**：ID 由**匹配器**维护，不由模型指定，也不由标题哈希推导。

匹配的**主键**是 `location`（归一化文件路径，**剔除行号**——行号会因无关改动漂移），
**辅键**是 `keywords` 集合。同一轮内新报的条目与台账里的 `open` 条目做匹配：

| 步骤 | 规则 |
|---|---|
| 1 | 路径相同 **且** 关键词 Jaccard 相似度 ≥ 0.5 → **同一条目**，沿用原 ID |
| 2 | 路径相同但关键词无交集，且编辑距离相似度 ≥ 0.75 → 视为同一缺陷的重新表述，沿用原 ID，并累加关键词 |
| 3 | 以上都不满足 → **新条目**，分配下一个未被占用的序号 |
| 4 | 模型自报的 `id` **一律忽略**（它只是给人看的提示） |

关键词提取规则（确定性，可测试）：从 `title` 中抽取 ASCII 标识符（`[A-Za-z_][A-Za-z0-9_]*`，
长度 ≥ 4，去除停用词）与反引号包住的片段；全部小写化。中文正文不参与匹配——中文分词
本身不稳定，正是第一版漂移的来源。

**这是本设计最关键的一处：** 匹配器是**确定性代码**，有钉住测试（§6 T1），
而不是"希望模型每轮用同样的话描述同一个问题"。

#### 3.1.3 状态转换表（补充 F-05）

| 从 | 事件 | 到 | 约束 |
|---|---|---|---|
| `open` | 提交 `commit` 证据 | `resolved` | commit 必须存在且是 HEAD 的祖先 |
| `open` | 提交 `command` 证据且退出码符合预期 | `disproved` | 命令必须可执行（§3.3） |
| `resolved` | 下一轮同路径同关键词的条目再次出现 | `open`（**reopen**） | 允许：修复可能被回退 |
| `disproved` | 下一轮再次出现 | 保持 `disproved` | **不可 reopen**：证伪是实测事实，不由模型推翻 |
| 任意 | 同一轮内两个席位报同一条 | 合并 | 保留先出现的 ID，`seat` 记为 `"multi"` |
| 任意 | 严重度被改高 | 采纳更高值 | 只升不降：降级需要证据，升级不需要 |

`disproved` 不可 reopen 是一条**刻意的不对称**：证伪靠实测，重开靠断言；后者不能覆盖前者。

### 3.2 轮次协议改造

**Round 1（匿名，不变）**：三席位独立评审，各自输出 `### Findings` 表。

**Round N≥2（改造）**：prompt 从「回传票型」改为「**回传条目台账**」：

```
上一轮台账（共 N 条）：
| ID | 严重度 | 标题 | 状态 |
|---|---|---|---|
| TC-01 | critical | prepare 阶段 catch 硬编码… | resolved（提交 abc123 修复） |
| TC-02 | major    | 无作用域正则改写 [tool.other]   | resolved（提交 def456 修复） |
| TC-03 | major    | 多行字符串里的 [x] 截断表体      | disproved（smol-toml 实测接受） |
```

席位被要求：**只对 `open` 条目的仍然存在性表态**，并重新列出仍未解决的条目。
被 `resolved`/`disproved` 的条目**不再作为反对理由**。

**收敛判据（替换 `delphi-run.ts:115`）**：

```
新共识 = 全部席位 APPROVED（3/3，与门禁一致）
         AND 无 open 的 critical/major 条目
```

`minor` 不阻断（与现行 `minor_concerns` 不进阻断语义一致）。

**⚠️ 这里必须读清楚（修订 F-03）**：第一版写的是「无 open critical/major **且至少 2 席
APPROVED**」——那已经是 2/3 语义，而同一份文档又说门禁不改、`consensus_ratio < 0.90` 仍 BLOCK。
**两份互相矛盾的规则同时存在，写出的证据永远进不了 pre-push。** 可行性席位 C 把这一条
列为 F-03 critical，是对的。

**本版**：`consensus_ratio` 的**计算方式一字不改**，仍是 `approvals / validCount`
（`delphi.ts:304`），门禁仍是 `>= 0.90`（`validate-code-walkthrough.cjs:576`）。
条目化**只影响"何时认为可以停止询问"**，不影响"什么叫通过"。

`findings[]` 是给**人**看的诊断信息，**不参与门禁判定**。这一点在 §5 里由 T7 钉住。

### 3.3 证伪冻结（G2，修订 F-02）

**第一版的错误**：`disprove(findingId, evidence: "命令 + 输出")` 里的 evidence 是自由文本。
编排者可以**自己写一段话说"实测不成立"**，然后把它冻结掉——这是**审的人给自己放行的后门**。

**本版方案**：证伪必须提交**可执行的结构化证据**，由系统实际执行，编排者不能只写结论。

```jsonc
{
  "kind": "command",
  "command": "node -e \"require('smol-toml').parse('[tool . mutmut]')\"",
  "expect_exit": 0,          // 期望的退出码
  "cwd": "."                 // 相对仓库根
}
```

| 约束 | 说明 |
|---|---|
| `kind` 白名单 | 只有 `command` 与 `commit`；自由文本不被接受，传字符串直接拒绝 |
| **命令由系统执行** | 编排者提交的是命令，**输出由系统自己捕获**，不采信编排者转述 |
| 失败即拒绝 | 命令退出码与 `expect_exit` 不符 → 证伪不成立，条目保持 `open` |
| 超时 | 默认 30 s；超时视为未执行，**不是证伪成立**（"没测"≠"证伪"） |
| `cwd` 限制 | 必须在仓库根之内；越界拒绝 |
| 审计 | 每次 `disprove` 追加一行到 `.sprint-state/delphi-disprovals.log`：时间、findingId、命令、实际退出码、输出摘要 |

**残余风险与承认**：上述约束阻止了"随口说一句就冻结"，但**不能**阻止编排者构造一条
始终返回 0 的假命令（如 `true`）。这是一处**有意的取舍**：完全消除需要独立复核者，而用户
已决定不引入额外人工。缓解措施是**审计日志可复核 + 输出由系统捕获**——造假会留下可查的痕迹，
而不是无处可查。这比第一版"自由文本"显著更强，但**不是零风险**，必须在文档里写清楚。

**这条直接对应 ADR-0004 的教训**：第 6 轮三条 critical 实测全部不成立，
但没有地方记录这件事，评审只能靠人读报告硬扛。

### 3.4 席位释放（G4，修订 F-04）

若某席位在上一轮已 `APPROVED`，且其提出的全部条目都已 `resolved`/`disproved`，
则本轮**跳过该席位**（不消耗 token）。结果里记录 `released: true`。

**修订 F-04：同意疲劳的缓解措施。**

第一版只有"跳过"，没有考虑：被释放的席位不再看到材料，**其他席位在后续轮次新指出的
跨领域缺陷它完全不知道**。三席都独立指出了这一点（A: Seat release blind spot,
B: re-engagement trigger, C: F-04）。

| 规则 | 说明 |
|---|---|
| 默认跳过 | 已 APPROVED 且条目全清 → 不重问 |
| **重新召回触发** | 只要任意一轮出现**新的 `open` critical**，本轮**召回全部被释放席位**，并要求它们只审这一条 |
| 释放不影响计数 | 被释放席位沿用上一轮的 APPROVED 票 |
| 重置条件 | 召回后若该席位改判 REQUEST_CHANGES，`released` 永久取消直到它再次 APPROVED |

⚠️ **安全约束**：释放只影响**是否重问**，不影响**共识计算**。必须写测试钉住：
**释放不能把一个原本 REQUEST_CHANGES 的席位变成 APPROVED**（§6 T5）。

### 3.5 阈值：不做可配置项（修订 F-03）

| 位置 | 现状 | 本版 |
|---|---|---|
| `delphi.ts:74-75` | 硬编码 90 | **保持不变** |
| `.delphi-config.json` | — | **不新增** `threshold_percent`：一个"可配置但门禁不认"的开关是陷阱 |
| `validate-code-walkthrough.cjs:576` | 硬编码 `0.90` | **保持不变** |

**为什么撤掉第一版的"可配置"（G3）**：
用户原本的决策是"只让阈值可配置、默认保持 90%"。但 F-03 让这件事的性质变了——
只要存在一个能让工具算出 `consensus_ratio = 0.67` 的入口，这个值就会被写进证据文件，
然后被 pre-push 无可挽回地拒绝。**一个只能产出被拒证据的开关，不是能力，是陷阱。**

所以本版**不提供**该开关。未来若要放开 2/3，必须**工具与门禁同时改**，作为一个整体决策
（届时需新的 ADR 记录偏离 3/3 的理由，参照 ADR-0004 的写法）。

## 4. 输入预算：一个必须说清楚的既有限制

Gate MW 对每个席位的输入预算是 **40 KB**。实测本次要改的文件：

| 文件 | 字节 |
|---|---|
| `plugins/dsh/src/delphi.ts` | 10 919 |
| `plugins/dsh/src/delphi-run.ts` | 7 954 |
| `scripts/delphi-external-review.cjs` | **36 112**（879 行） |
| `githooks/lib/validate-code-walkthrough.cjs` | **31 182**（725 行） |

**`delphi-external-review.cjs` 单独就占掉 40 KB 预算的 90%。** 本设计的 S1 改动本就在
`delphi-run.ts`（8 KB）+ `delphi.ts`（11 KB）≈ 19 KB，**在预算内**；
但 S2 触及 runner 和门禁时，**单次评审无法同时覆盖两个文件**，必须拆成两次评审。

> **这条同时是一个设计约束**：改造 `delphi-run.ts` 时**不得让它膨胀到需要与
> `delphi.ts` 分开送审**。若超过约 30 KB，就把 prompt 构造拆成独立模块
> （本设计已把 §3.2 的 prompt 改造预留在 `delphi-run.ts`，需持续盯住行数）。

### S0 — 纯新增，零冲突（**现在就能做，不触碰任何现有文件**）

### 门禁侧的最小改动

`validate-code-walkthrough.cjs` 只在**证据含 `findings[]`** 时做一致性检查：
**若存在 `open` 的 critical 条目，`consensus_ratio` 不得为 1.0**。缺失该字段时按旧语义。
这是**防伪造**，不是放宽——它只会让判定更严，不会更松。

## 6. 验收判据与钉住测试

TDD 先行，以下测试必须在实现前变红：

| # | 测试 | 钉住什么 | 反例（必须红） |
|---|---|---|---|
| T1 | 同一 finding 措辞微调（换标点、加行号、改中文措辞）后 ID 相同 | §3.1.2 匹配器 | 用标题哈希或行号做 ID |
| T1b | 关键词数 <2 时不得按 Jaccard 判定同一条 | §10.1(a) 误合并 | 单关键词即同 ID |
| T1c | 已 `disproved` 的条目换个 `location` 重报，仍匹配到原 ID（不放行） | §10.1(b) 绕过冻结 | 换路径即得新 ID |

| T3 | 自由文本 evidence 的 `disprove` 被拒绝；命令退出码不符时证伪不成立 | §3.3 | 接受 `"我测过了，不成立"` |
| T3b | 命令超时 → 条目保持 `open`（不是证伪成立） | §3.3 "没测≠证伪" | 超时当成通过 |
| T4 | 已 APPROVED 且条目全清的席位被释放，沿用 APPROVED 票 | §3.4 | 释放导致席位丢失 |
| T5 | 原本 REQUEST_CHANGES 的席位**不会**因释放变成 APPROVED | §3.4 安全约束 | 释放实现成"跳过即通过" |
| T6 | **快照/黄金测试**：未启用条目化时，一段固定的三席位报告产出的票型、`consensus_ratio`、文本与今天一致 | 回归底线 | 默认路径行为漂移 |
| T7 | 证据含 open critical 时 `consensus_ratio` 不得为 1.0 | §5 防伪造 | 台账与比率脱钩 |
| T7b | 评审工具产出台账时，证据**省略 `findings[]`** 不得通过门禁 | §10.1(c) 规避检查 | 省略字段即按旧语义放行 |
| T8 | 所有新增/修改函数 CCN < 5 | Gate 3 | 新逻辑塞回大函数 |
| T9 | 出现新的 open critical 时，被释放席位**被召回** | §3.4 修订 F-04 | 释放后永久失联 |
| T10 | `disprove` 的 `cwd` 越出仓库根被拒绝 | §3.3 客户端约束 | 任意路径执行 |

**T6 的表述修订（F-06）**：第一版写"逐字节一致"，技术席位 B 指出**不可达**——prompt 一改，
模型输出就会变。改为：**在"条目化未启用"的默认路径上，给定固定的席位报告，
`consensus_ratio`、`verdict` 判定、`formatOutcome` 输出必须与黄金文件一致**。
用**快照测试**实现，而不是"跑一遍看看像不像"。

**兼容边界必须写明**：真正的端到端一致性做不到（模型非确定性），所以 T6 钉的是
**我们的代码在这些输入下的行为**，不是模型的输出。

## 7. 与活跃重构的并发约束（修订 F-07）

**现状**：主分支 `refactor/orthogonal-decomposition` 正在按函数削减 CCN，
`.ccn-baseline.json` 中 **301 个函数仍 > 5**。

**本版改为按文件所有权推进，而不是等整个重构完成**：

| 阶段 | 触及的文件 | 重构方近期是否在改 | 开工条件 |
|---|---|---|---|
| S0 | 仅**新增** `delphi-finding.ts` | 否（新文件） | **可立即开工** |
| S1 | `delphi.ts` / `delphi-run.ts` | 是（`runReview` CCN 39） | 该文件最近一次重构已合入 |
| S2 | `delphi-external-review.cjs` / 门禁 | 是（逐函数削减） | 同上，且必须拆两次评审 |

**仍然不允许的反模式**：
- 两边**同时**在 `runReview` 上动手（一个拆函数、一个加逻辑）；
- 在重构期间改 `plugins/dsh/src/delphi.ts` 并 resync 镜像，导致重构方的 CCN 基线失效。

**这与项目既有教训一致**：`AGENTS.md` 的 PUSH RHYTHM 章节说"小推送是更便宜的选择"，
而这里的对应结论是——**同一文件上叠加两个并发重构，比先后做贵得多**；
但**只新增文件**的改动没有这个问题，所以 S0 不该等。

## 8. 被否决的替代方案（记录理由，避免重复讨论）

| 方案 | 否决理由 |
|---|---|
| **三席位同视角 + 2:1 通过** | §1.3：用发现能力换速度。ADR-0004 证明缺陷是单点命中，不是多数同意。 |
| 提高 `max_rounds` 到 8 | 不解决任何根因，只延长同一次僵局。ADR-0004 的六轮里第五、六轮已是噪声。 |
| 降低到 2 名专家 | 违反 Delphi 不变式（三专家互异模型），且 N=2 有平票死锁。 |
| 让席位直接改代码 | 评审与实现混为一体，违反 `skills/delphi-review` 的 Scope 声明。 |
| 只改门禁阈值（不改评审工具） | 治标：门禁放宽了，评审工具照样跑 5 轮，成本没降。 |
| **阈值可配（第一版 §3.5）** | 产出的是门禁必然拒绝的证据——只能算 0.67 的开关，是陷阱不是能力。见 §3.5。 |
| **标题哈希做 finding ID（第一版 §3.1）** | 中文措辞微调即漂移，冻结静默失效。改为三要素匹配。见 §3.1.2。 |
| **自由文本 disprove（第一版 §3.3）** | 编排者可以自己写一段话就放行自己。改为结构化可执行证据 + 审计。见 §3.3。 |

## 10.1 复审通过时的非阻塞建议（采纳，并入 S0）

R3 一致性通过（3/3，100%）时，可行性席位 C 给出 7 分并附三条建议。**三条均采纳**——
其中 (b)(c) 是实质漏洞，不是风格问题：

| # | 建议 | 为什么必须收（不是"建议"） | 落点 |
|---|---|---|---|
| (a) | Jaccard 0.5 在关键词极少时易误合并：设最小关键词数下限 ≥2，并对 step 2 补「关键词并集后再匹配」 | 只有一个关键词时 Jaccard 只有 0 或 1，等于退化成"关键词相同即同一条" | §3.1.2 + T1b |
| (b) | 匹配器必须登记**已 `disproved` 条目**的关键词，防止同一缺陷换路径重报后被分配新 ID | **绕过冻结的现成路径**：换个 `location` 写同一个问题，就得到新 ID，冻结失效 | §3.1.2 + T1c |
| (c) | 门禁侧「open critical ⇒ ratio≠1.0」**仅在 `findings[]` 存在时生效**，省略该字段即按旧语义通过 | **证据方可以省略 `findings[]` 规避检查**——防伪造形同虚设 | §5 + T7b |

**(c) 的处置**：S2 阶段必须在门禁里把 `findings[]` 从「可选」升级为「当评审工具产出了条目台账时必填」。
短期（S2 之前）的过渡措施：**审计日志与台账分开落盘**，即使证据 omission 也留有痕迹。

**T1b / T1c / T7b** 加入 §6 测试表。
