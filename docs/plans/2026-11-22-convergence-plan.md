- 关联：#789（架构正交分解索引）、#816（P0 止血批次 0.38.5）、`2026-11-15-open-issue-triage-and-plan.md`

## 0. 一句话结论

**open issue 数量不是当前的主要问题——"产生 issue 的速度"才是。**
按最近 45 天的实测：开了 181 个、关了 85 个，净值 **+96**，而且新增速率没有下降。
在这个速率下，任何"逐个修 issue"的排期都会以"修不完"结束。

第二个结论更重要：**这些 issue 不是 96 个独立缺陷，是 1 个体系缺陷的重复输出。**
本机最近 45 天的审计日志给出了它的度量：

| 事实 | 数值 | 出处 |
|---|---|---|
| SKIP 占全部门禁记录 | **8%**（933/11175） | `.xp-gate/audit.jsonl`，45 天 |
| SKIP **没有带任何原因** | **49%**（457/933） | 同上 |
| 带原因的 SKIP 中，"最该有原因"的那几个门禁 | gate-4/6/9/10 的 SKIP **全部无原因**（89/101/19/91） | 同上 |
| 一次提交的审计里被标 SKIP、却同时记 `passed:true` 的记录 | 例如 `gate-10 SKIP` 且 `duration_ms=206651`、`gate-6 SKIP` 且 `duration_ms=9010` | 同上 |

也就是说：**门禁花 3 分 26 秒跑完，记为 SKIP，同时记 passed。**
这正是 `AGENTS.md` 里写着的最高优先不变式被违反的样子——`"not checked" must never be
indistinguishable from "passed"`。这不是某一个门禁的 bug，而是**产出层没有第三态**，
于是每个门禁各自用自己的方式把"没查"写成"没问题"，每修一个又冒出新的一个。

**所以收敛的杠杆点不是"修 issue"，是"让 issue 不再产生"。** 本计划据此重排优先级。

## 1. 诊断：三个正在互相喂养的循环

用户描述的"任务混在一起、总也结束不了"，实测下来是三个闭环，不是一个 backlog：

### 循环 A — 缺陷产出循环（主要矛盾）

```
门禁漏检 → 缺陷合入 → 用 xp-gate 开发新项目时撞见 → 记 issue
      ↑                                              ↓
      └────── 修 issue 时改动门禁，又被同一批漏检门禁放行 ←┘
```

证据：**最近 45 天开的 181 个 issue 里，相当一部分是在"用 xp-gate 开发 xp-gate"时撞见的**
（#858/#859/#860/#848/#847/#846 都属这一类），而它们被记录为"xp-gate 的缺陷"而不是
"新项目的需求"。这就是为什么"继续用 xp-gate 开发新项目"会持续制造 xp-gate 的工作量。

### 循环 B — 修复成本循环（第二矛盾，即用户说的"性能问题"）

实测（`.xp-gate/audit.jsonl`，按 commit 聚合，45 个代表提交）：

| 指标 | 数值 |
|---|---|
| 单次提交门禁净耗时 **中位数** | **89.6 s** |
| 慢的例子 | 556 s / 570 s / 338 s（gate-10 单门 ≥200 s 出现 3 次） |
| gate-12 中位 / p90 / max | 13.9 s / 49.9 s / 143.6 s |
| gate-5 中位 / p90 / max | 16.7 s / 71.6 s / 289.7 s |
| gate-0 p90 | 19.6 s |

**这解释了"修一个 bug 特别慢"**：不是自动化测试本身慢，是**每验证一次改动要付 ~90 秒**，
且方差极大（同一份代码可能 42 s 也可能 570 s）。一次缺陷修复通常要验证 3–5 次。
`2026-11-10-test-suite-speed-baseline.md` 已经把 vitest 侧从 370 s 压到 123 s，
**但提交侧（pre-commit 15 道门）从未被这样测过——这是性能任务里最大的一块未开发区**。

### 循环 C — 上下文/分支循环（放大器）

| 现象 | 实测 |
|---|---|
| 三个长分支长期不合并 | `chore/orthogonal-decomposition` 领先 2086、`release/issue-fixes` 2080、`release/php-gate4` 2074（均落后 2104）——**三条都是同一批提交的重复副本**（同一 SHA 内容在两个名字下各存一份） |
| 三个 worktree 同时在跑 | `.` / `xp-gate-p1e` / `xp-gate-release` |
| 挂在 worktree 上的历史分支 | `feat/arch-doc-guard`、`fix/gate-6-layer-config-forms`、`fix/gate-6-yaml-forms-811` 在 git 里**已不存在**，只剩目录 |
| 计划文档 | `docs/plans/` 共 **109 份**，11-15 之后只有 4 份（收敛了，好） |
| 设计文档里未解答的"需用户拍板" | `2026-11-09-architecture-orthogonal-decomposition.md` §7 的 4 个问题，**13 天未答**，而 P1-A 是它的入口 |

分支不收口 → 每次改动要在三处重复验证 → 循环 B 的成本 ×3。

## 2. 这 96 个 open issue 实际分几类（按"是否同一个根因"重排，不按编号）

用标签粗分是错的（`migrating-to-wsl` 覆盖了 42 个、从 P0 到纯提案全光谱，无信息量）。
按**根因簇**重排后是这样：

| 簇 | issue 数（估） | 根因 | 一句话 |
|---|---|---|---|
| **C1 产出层无第三态** | ~22 | 报告/审计/退出码没有"未测量"态 | 修完一个，下一个门禁照样漏 |
| **C2 执行面不唯一** | ~14 | hook / CLI / skill 三面各一套逻辑 | 在 CLI 修好、hook 里没修 |
| **C3 部署链路多份清单** | ~12 | 装哪些文件手写 4 处 | 装了但没生效 / 卸不干净 |
| **C4 语言适配器登记不全** | ~10 | 语言靠手写名单 | `.mjs` `.dart` `.objectivec` `.rs` 等逐个漏 |
| **C5 工具探测/环境不一致** | ~8 | doctor vs gate 解析口径不同 | 带 `~/.local/bin` 的能用，doctor 说没有 |
| **C6 性能** | ~6 | 提交侧无增量、无缓存 | 每改一次 90 s |
| **C7 真·独立缺陷** | ~15 | 各自独立 | 可以逐个修，不再生 |
| **C8 设计/索引单** | ~9 | 不是缺陷 | 不该占 issue 列表 |

**关键判断：C1–C6（约 72 个，占 75%）修完一批后会自然停止产生新 issue；C7/C8 不会。**

上一轮规划（`2026-11-15-open-issue-triage-and-plan.md`）给的是"按优先级 P0→P3 排期、逐个修"。
实测数据显示这条路走不通：**P0 修了 6 个之后，5 天内又新开了 37 个**（11-16 ~ 11-22 的开单数）。
本计划改为**按根因簇一次修一类**。

## 3. 建议的收敛路线：3 个阶段，每个阶段有一个"可发版判据"

不按周排，按**判据**排——因为在这台机器上，时间估算没有可信度（见 §5）。

### 阶段 0：止血 + 决定（0.5–1 天）——必须先做，因为它能立刻降低后续一切的成本

1. **分支收口**：把 `chore/orthogonal-decomposition` / `release/issue-fixes` / `release/php-gate4`
   的内容与 main 逐一核对，**保留真正未合入的，其余删除**；清理 3 个 worktree 中的 2 个。
   判据：`git branch` 只剩 main + 至多 1 条在飞分支；`git worktree list` 只剩 1 个。
2. **回答 `2026-11-09` §7 的 4 个决策**（见 §4）。这 4 个答案决定了后面 5 个 sprint 的边界，
   它们已经卡了 13 天，是当前**唯一**真正需要用户拍板的东西。
3. **建立"issue 预算"规则**：从今天起，新增 issue 必须挂到 C1–C7 某一簇上，
   并注明"这是新缺陷还是已知簇的又一例"。前者进 backlog，后者挂到已有工作项下不再单独计数。
   判据：一周后 `gh issue list` 的**簇分布**比总数更有信息量。

### 阶段 1：让"没查"变成可判定的（目标：0.39.0）——最高杠杆

**修 C1 + C2 两个簇。** 这是唯一一个"修完就不用再修同类"的动作。

1. **统一 verdict schema，引入 `NOT_CHECKED` 第三态**（吸收 #800 #792 #813 #851 #852 #826 #838）
   - 断言：`gate_status ∈ {PASS, SKIP(with reason), NOT_CHECKED(with reason), FAIL, WARN(with reason)}`
   - **无 reason 的 SKIP 必须是一条独立可加的失败**——本机实测 49% 的 SKIP 无原因，
     这条规则一旦生效，等于一次性暴露 457 条此前被吞掉的"没查"。
   - 审计层先修：`gate_status=SKIP` 与 `passed:true` 必须在 schema 层互斥。
2. **单一 verdict 生产者**（吸收 #778 #715 #784 #852）
   - `#789` 的评审记录已经给出正解：**"三入口产出字节相同 verdict"不可实现，正解是 CLI 成为唯一生产者，hook 与 skill 都是它的消费者**。按这个做，不要再对拍。
3. **可测的验收，不是"修好了"**：
   - 一个**故意会漏检的 fixture 仓库**（含真违规），断言三道入口都给出 FAIL 且退出非零。
   - 该 fixture 进 nightly，**这就是"门禁是否有用"的持续答案**（用户第 2 个任务"确认这些门禁是否有效"由它回答，而不是靠逐个人工核对）。

**判据（阶段 1 完成的定义）**：在同一个 fixture 上，`xp-gate check --gates <N>` 与
`git commit` 触发的 hook 对同一违规给出**相同 verdict**，且 SKIP 100% 带原因。
达成后 C1/C2 两簇的 ~36 个 issue 应一并关闭——**且此后不再新开同类**。

### 阶段 2：把"验证一次"的成本降到可接受（目标：0.39.1）

**修 C6（性能）。** 必须在阶段 1 之后做，因为阶段 1 会改变门禁的判定逻辑，
反过来会作废这轮的性能基线。

1. **先测再动**：本机真实负载实测两次为 32.8%，日记账里"90–100% CPU"的结论需要按
   `~/.dsh/AGENTS.md` 规则 6 重新校验（`2026-11-10` 文档 §15 已经推翻过 `LoadPercentage`）。
   性能基线必须用 **CPU 差分**测，并记录每组负载。
2. 按实测排序动手——目前证据指向这三项（**都是提交侧，不是 vitest 侧**）：

   | 目标 | 当前证据 | 检查方式 |
   |---|---|---|
   | gate-10 长尾（≥200 s 出现 3 次） | 中位仅 261 ms，p90 66 s，max 216 s | 偶发，先定位触发条件 |
   | gate-12（中位 13.9 s、p90 49.9 s、max 143.6 s） | 271 次记录 | 是否每次全树扫描 |
   | gate-5（中位 16.7 s、p90 71.6 s、max 289.7 s） | 174 次记录 | `--coverage` 是否仍恒开（#640） |

3. **完成判据不是"快了 X%"，而是"分布变窄"**：单次提交门禁时长 p90 从 71.6 s 降到 <30 s，
   且 max < 60 s。中位数已经不高，**用户感受到的慢是长尾，不是中位**。

### 阶段 3：把剩下的独立缺陷一次性清掉（目标：0.39.2 = 稳定版）

**只做 C7（~15 个真·独立缺陷）**，且**先修 C4/C5 的语言与工具簇**，
因为用户明确还要加 C# / PHP / Rust 等语言——**在 C1 没修之前加语言，只是给同一个漏洞多加一个入口**。

**稳定版判据（这就是"稳定"的定义，可验证）**：
1. Gate 覆盖矩阵（`xp-gate gate-capability`）中，每个语言的每个门禁只有
   `PASS / FAIL / NOT_CHECKED(理由)` 三种状态，**没有空原因**。
2. 在 3 个真实消费项目（含至少一个非 TS 项目）上各跑一次全量，**0 个 fail-open**。
3. 连续 20 次提交，`NOT_CHECKED` 与 `SKIP` 的比例与原因分布**不再出现未知模式**。
4. open issue 清单中 C1–C6 清零，只剩 C8（索引单，标 `needs-decision` 冻结）。

达到 4 条后把 VERSION 提到 `1.0.0`，**冻结功能开发**，此后新语言/新门禁进下一个大版本。

## 5. 关于时间估算：本计划刻意不给

`2026-11-10` 文档已经证明这台机器上单次 wall-clock 读数不可用（同一份未改动代码测出
182.9 s 和 62.2 s，差 3 倍；worker 数 ABBA 同一配置两次差 42%）。
我自己今天的复测：真实 CPU 占用 **32.8%**，与仓库文档里历次记录的"负载 90–100%"矛盾。

**在这个测量分辨率下给出"还需 X 天"是不诚实的。** 本计划改用**判据**驱动：
每个阶段结束时有一个可机械验证的判据（§3 每节的"判据"），判据不达成该阶段不算结束。
这样进度是可观测的，而耗时是可变的。
