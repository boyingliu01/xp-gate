# 迭代速度优化设计（Iteration Speed: 65s/150s → 6.5s/15s）

**日期**: 2026-11-07
**目标**: 两个场景的端到端迭代时间压缩到基线的 **10%**
**基线**: `2026-11-07-iteration-speed-baseline.md`
**状态**: 待评审

---

## 0. 一句话结论

**当前迭代慢不是因为门禁太严，而是因为门禁各自为政、且把"验证这棵树"做成了"每次重扫整棵树 + 每次去网上重下规则"。**

实测证据（同一台机器、同一仓库）：

| 门禁 | 它实际做的事 | 实测 | 真正需要的时间 |
|---|---|---:|---:|
| Gate 1 | `npx eslint .` — 全树 2000+ 文件 | **24.3 s** | 3.7–4.5 s（只 lint 改动的文件） |
| Gate 5 | `vitest run --coverage` — 跑 1 个测试文件却给整棵树插桩 | **34.7 s**（无覆盖率时 **5.1 s**） | 5.1 s |
| Gate 10 | `semgrep --config=p/security-audit` — **每次联网拉规则，本机超时** | **100–200 s** | 本地规则后 < 2 s |
| Gate 6 | `archlint scan .` — 全树 | **29.9 s** 冷 / **12.5 s** 热 | 2.3 s（按目录 + 缓存热） |
| Gate MP | 全树 `diff -rq` 47 组镜像 + 5 棵树 | **10–32 s** | 只比对本次改动涉及的镜像家族 |
| Gate 13 | 无条件探测 g++(0.5s)+javac(2.4s)+dotnet(0.7s) | **3–5 s** | 无 C/C++/Java/C# 文件时 0 s |

**这些都是"全量重算"而非"增量判断"。** 把全量换成增量，就是 10 倍收益的来源。

## 3. 优化项（按收益排序）

### O1 — Gate 10：禁止每次联网拉规则 【最大收益，且是缺陷修复】

**现状**：`SEMGREP_RULES=(--config=p/security-audit)`。`p/xxx` 是 semgrep **registry 引用**，
每次运行都会去 `semgrep.dev` 拉规则。实测本机该请求 read timeout，semgrep 一路重试到
hook 的 180 s 超时，然后降级为 SKIP——**每次 TS 提交白付 1–3 分钟，且实际上什么都没扫**。

**这不是"慢"，这是"没扫还号称跑了"**：日志写 `SAST (semgrep timed out after 180s)` 然后 SKIP，
但 30 次提交里 Gate 10 的 200 s 样本就是这么来的。

**改法**：
1. 规则固化到仓库：`.semgrep/rules.yml`（把 `p/security-audit` + `p/csharp` 的内容 vendor 进来），
   Gate 10 用 `--config .semgrep/rules.yml`。
2. 若本地规则文件缺失，**明确降级并在报告里标 `no_local_rules`**，不是静默 SKIP。
3. `XP_GATE_SEMGREP_TIMEOUT` 默认从 180 s 降到 60 s（本地规则下 2 s 内完成，超时即异常）。

**为什么这是"不降低检出能力"**：vendor 的是同一套规则内容，扫描对象不变，只是不再联网。

**风险**：规则更新需要手动 vendor。用一条 CI 任务每周探测 registry 版本变化并提 PR 解决。

**验收**：Gate 10 单次 < 2 s；制造一个已知漏洞（如 `eval()` 拼接）必须 BLOCK。

---

### O2 — Gate 1：ESLint 已经是增量的，不要改（原判断有误，已更正）

> **更正记录（2026-11-07）**：本节初稿断言"Gate 1 跑 `npx eslint .` 全树"。**这是错的。**
> 核对 `githooks/pre-commit:1792` 后确认：pre-commit 的 TypeScript 分支**本来就是 diff 作用域**——
> `ESLINT_FILES=$(echo "$CHANGED_FILES" | grep -E '\.(ts|tsx|js|jsx)$')`，只 lint 改动文件。
> 我测到的 24.3 s / 53 s 是**直接手跑 `npx eslint .`** 的结果，不是 hook 里发生的事。
> 两者实测对比（同一调用形式）：单文件 3.9 s vs 全树 53 s。
>
> 真正的全树调用只存在于 `githooks/adapters/typescript.sh:64`（`run_lint()`），而
> `run_lint` 在 pre-commit 里**只有一处调用点**（第 2373 行，通用 adapter 兜底分支 `*)`），
> TypeScript 走的是自己的 `typescript)` 分支，**不经过 `run_lint`**。

**结论：Gate 1 不需要优化，`run_lint` 的全树调用对 TS 项目是死代码。**

**仍然成立的小改进**：pre-commit 用 `run_node_bin eslint eslint/bin/eslint.js`（已是），
不要退回 `npx eslint`（`npx` 解析层实测多 2–3 s）。

**遗留问题（独立于性能）**：`githooks/adapters/typescript.sh:64` 的 `npx eslint .` 是
**全树**调用，虽然对 TS 项目不可达，但任何落到通用分支的 JS/TS 项目都会吃到这个全树成本。
建议改为接收文件参数——但这是**死代码清理**，不是本次提速的主力，别把它算进 10%。

**验收**：Gate 1 单次 < 5 s；在改动文件里写 `as any` 必须 BLOCK；全量 `npm run lint` 仍可用。

### O3 — Gate MP：从全树比对改为"本次改动涉及的镜像家族"

**现状**：`scripts/check-hook-mirror.sh` 无条件对比 47 组文件 + 5 个目录树，稳定 10–11 s，
push 时实测 10–32 s。

**改法**：
1. 脚本新增 `--changed <path>...`：只比对与给定路径相关的镜像对。
2. pre-push 传入本次 push 的改动文件（已有 `PUSHED_FILES`）。
3. **保留全树模式**（`--all`）给 CI 和 `xp-gate doctor`；pre-push 用增量。
4. 若改动文件与任何镜像家族无关（如只改 `docs/`），**直接 0 成本跳过**。

**为什么安全**：镜像漂移只可能出现在"被改动的 canonical 文件"上——没被改的文件不会突然
与镜像不一致。真正需要全树的场景（新增/删除镜像文件）由**文件清单比对**兜住，那是 O(1) 的。

**验收**：只改 hook 时 Gate MP < 0.5 s；只改一个 canonical 文件不同步镜像时仍 BLOCK；
CI 全树模式仍能发现历史漂移。

### O4 — Gate 6：archlint 按目录作用域 + 利用其内置缓存

**现状（实测）**：

| 调用 | 冷启动 | 缓存热后 |
|---|---:|---:|
| `archlint scan .`（全树） | 29.9 s | **12.5 s** |
| `archlint scan src/architecture`（目录） | 12.7 s | **2.3 s** |

**关键约束（已验证，决定了改法）**：archlint 的 `[PATH]` 只接受**目录**，不接受单文件；
且它的检测器本质上是**跨文件**的（循环依赖需要整个依赖图、DeadCode 需要可达性、
GodModule 需要模块全貌）。所以**不能简单地"只扫改动文件"**——那样会漏掉跨文件的结构性问题。

**改法**：
1. 把改动文件去重成**父目录集合**，传给 archlint（而不是 `.`）。
2. **不再传 `--no-cache`**，让 archlint 复用其内置缓存（这是 12.5 s → 2.3 s 的来源）。
3. 改动横跨过多目录时（阈值如 >8 个），回退为全树扫描——此时缓存效应也已足够。

**为什么安全**：按目录扫仍然构建完整的依赖图（只是范围小了），循环依赖/上帝类/
死代码这些跨文件检测在受影响目录内仍然成立。全树扫描保留在 CI。

**风险**：跨目录的循环依赖（A 在 dir1、B 在 dir2）可能漏检。**这一点必须在评审中明确接受
或改为全树**——它是本设计里唯一一处"提速可能降低检出"的地方，不能用"反正还有 CI"糊弄过去。

**验收**：Gate 6 < 3 s（缓存热）；在改动目录内引入循环依赖必须 BLOCK；
跨目录循环依赖的检出能力需明文记录为 CI 兜底。

### O5 — Gate 13 / 11 / 7：无内容可检时 0 成本短路

| 门禁 | 现状 | 改法 | 收益 |
|---|---|---|---|
| Gate 13 | 无条件探测 g++(0.5s)+javac(2.4s)+dotnet(0.7s) | 先看 diff 有无 C/C++/Java/C# 文件，无则直接 SKIP，**不探测任何工具** | 3–5 s |
| Gate 11 | 非 sprint 项目仍子进程调 `sprint-gate.sh` | 先判 `.sprint-state/` 是否存在，无则内联 SKIP | 2–2.6 s |
| Gate 7 | 无 IaC 文件仍走探测 | 已在改（`No IaC files changed`），确认无残留探测 | 0.9 s |

**这是纯收益**：没有对应文件时，工具探测不可能发现任何东西。

### O6 — Gate 5：去掉 pre-commit 里的 v8 覆盖率 【实测 29 s 的纯浪费】

**现状（实测，单测试文件）**：

| 调用 | 实测 |
|---|---:|
| `vitest run <1 file> --coverage` | **34.7 s** |
| `vitest run <1 file>` | **5.1 s** |

**为什么是纯浪费**：`coverage.include` 是 `['src/**/*.{ts,js}', 'plugins/**/*.ts']`，
所以**哪怕只跑 1 个测试文件，v8 也要给整棵树（约 300 个源文件）插桩**。而这样算出来的
数字在子集运行时毫无意义——日志自己都写：

```
⚠️  Partial coverage 0% (subset test run, not full suite).
```

紧接着又出现：

```
ERROR: Coverage for lines (0.12%) does not meet global threshold (78%)
```

hook 里靠"检测到 'does not meet global threshold' 且 0 失败测试 ⇒ 跳过阈值判断"这个
**字符串匹配**把错误吞掉了（#473）。也就是说：**花 29 s 算出一个 0.12% 的错数字，
再靠匹配错误文案把它跳过。** 这正是"为了跑而跑"的典型。

**改法**：pre-commit 用 `vitest run`（无 `--coverage`）；覆盖率由
`npm run test:coverage`（全量，CI 跑）保证。

**为什么安全**：覆盖率阈值的正确作用域本来就是**全量套件**，子集运行不可能给出有效数字。
CI 的 coverage job 不受影响。

**验收**：Gate 5 子集运行从 15–35 s 降到 5–6 s；CI 覆盖率门禁仍生效；
`npx vitest run --coverage` 全量仍能正确报错。

### O7 — 减少 `node -e` 子进程（W4，中等收益）

pre-commit 有 25 处 `node -e`、68 处 `git`。Windows 下 `node` 启动 ~90–200 ms。
把纯 JSON 读取的 `node -e` 换成 bash 内置（或一个常驻的 node 辅助脚本一次性算完）可省 1–2 s。

**收益小，放最后**，且收益依赖机器，不作为达标的主要手段。

## 4. 关键约束：不能靠关掉门禁换速度

这是本设计最重要的部分。**10% 不是"少跑几个检查"换来的。**

每个被改成"增量"的门禁，都必须满足：

1. **缺陷仍然被拦住**：有 BATS/vitest 用例证明在缺陷真实存在时会 BLOCK。
2. **降级必须可见**：任何 SKIP 都带 reason，且 `xp-gate gate-coverage` 不把 SKIP 读成 PASS
   （该机制已存在，见 AGENTS.md）。
3. **全量路径保留**：CI 仍跑全树。pre-commit/pre-push 只做"本次改动的增量判断"。

尤其是 O1：它现在是**假通过**（超时后 SKIP，日志看起来像跑过了）。修完之后
Gate 10 才算真的在跑。所以 O1 既提速又**提高**了保障。

## 5. 实施顺序与预期

| 阶段 | 内容 | 场景一 | 场景二 | 风险 |
|---|---|---:|---:|---|
| 基线 | — | 65 s | 150 s | — |
| P1 | O1（semgrep 本地规则） | 65 s | ~50 s | 中（规则 vendor） |
| P2 | O6（去覆盖率）+ O2（eslint diff） | 65 s | **~25 s** | 低 |
| P3 | O4（archlint 按目录 + 缓存） | 65 s | **~17 s** | 中（跨目录循环依赖） |
| P4 | O3（Gate MP 增量） | **~35 s** | ~15 s | 低 |
| P5 | O5（短路）+ O7（子进程） | **~6 s** | **~15 s** | 低 |

> 说明：场景一的 hook 改动**也会触发 Gate 1 的 shellcheck 分支**（已是增量，0.5 s），
> 但会触发 Gate 10（`.sh` 在匹配清单里，semgrep 对 `.sh` 无规则但**仍会联网拉规则**）。
> O1 修好后场景一也受益。场景一的真正大头仍是 Gate MP（10–32 s），必须到 P4 才下降。

**预计最终**：场景一 ~5–6 s（**8–10%**），场景二 ~15 s（**10%**）。

## 6. 需要评审拍板的三个问题

1. **O1 的规则 vendor 方式**：直接把 `p/security-audit` 的 YAML 复制进仓库，还是保留
   `--config=p/security-audit` 但加本地缓存 + 离线回退？（前者彻底、后者自动跟进上游）
2. **O2 的语义边界**：pre-commit 只 lint 改动文件，意味着**未改动文件的历史告警不再被
   pre-commit 看到**。是否接受？（CI 全量 lint 仍在）
3. **Gate MW 绑定精确 HEAD（W5）**：这是场景一/二共同的最大"隐性成本"——改一行就让上一轮
   的走查证据作废，必须重跑 Delphi 评审。但这是**流程设计**问题，不是性能问题，
   本设计**不动它**，另案讨论。

## 7. 不做什么

- 不改 Gate 的**判定阈值**（覆盖率 80%、CCN 10、变异分数等）。
- 不引入 `--no-verify` 或新的绕过开关。
- 不为了速度删掉任何门禁。
- 不动 Sprint Flow / Delphi 流程。
