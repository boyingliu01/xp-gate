# XP-Gate 自身架构治理：从「故障高发 + 性能恶化」往回推

- 日期：2026-11-07
- 状态：诊断 + 方向，待评审
- 关联：#686 / #728 / #640 / #649 / #632 / #633 / #658
- 前置：`2026-11-07-gate-6-layer-enforcement-design.md`（Gate 6 分层强制）

---

## 0. 一句话结论

XP-Gate 的问题不是「某个门禁坏了」，而是**它从来没有对自己执行它要求别人做到的事**。

它检查目标项目的重复代码、复杂度、分层、镜像一致 —— 而它自己：

- **49.8% 的行是镜像副本**（11.4 万行，其中 80% 是字节相同的纯复制）
- **同一套门禁最多有三个实现**（shell 给 hook、TS 给 CLI、镜像给 npm 包）
- **没有任何机制保证这三条路径得出相同结论**

`#649` 自己写过这句话：

> 镜像/路径漂移类返工（58 次失败）：**这是架构约束不是代码风格，应工具自动化而非提示词自律。**

这句话是对的，但它被写在一个 issue 里，没有变成架构。

## 1. 实测：这个仓库到底有多大

`git ls-files` 全量统计（含测试、含镜像）：

| 分类 | 文件 | 行数 | 占比 |
|---|---:|---:|---:|
| **镜像** `src/npm-package/` | 488 | 114,019 | **49.8%** |
| 测试 | 434 | 71,407 | 31.2% |
| 生产 `src/` | 89 | 16,282 | 7.1% |
| 生产 `githooks/` | 65 | 14,168 | 6.2% |
| 生产 `scripts/` | 34 | 6,810 | 3.0% |
| 生产 `plugins/` | 27 | 5,219 | 2.3% |
| 生产 `skills/` | 2 | 94 | 0.0% |
| 其他 | 11 | 998 | 0.4% |
| **合计** | **1,150** | **228,997** | |

**真实生产代码 4.3 万行。仓库里躺着 22.9 万行。**

这个比例本身就是最大的架构问题：**你在维护的东西，是你以为在维护的东西的 5 倍。**

### 1.1 镜像的真实构成

1006 个镜像文件中：

- **809 个（80%）与生产代码字节完全相同** —— 纯复制，零信息
- 197 个有差异（配置、入口、自研测试）

`check-hook-mirror.sh` 守护 **38 个 hook 镜像 + 12 个 root 镜像**。
每改一个 canonical 文件，需要记得同步 1–2 处。**靠人记。**

### 1.2 镜像漂移是活的

写这份文档时，我改完 `githooks/pre-commit` 还没同步镜像，立刻产生 52 行漂移。
这不是假设，是**每次改动的默认状态**。

## 2. 为什么「故障高发」是结构性的

### 2.1 一因多实现

| 门禁 | shell 实现 | TS 实现 | 用途 |
|---|---|---|---|
| Gate 3 | `githooks/adapters/gate-3.sh` | `src/gates/gate-3.ts` | CLI |
| Gate 7 | `githooks/adapters/gate-7.sh` | `src/gates/gate-7.ts` | CLI |
| Gate 8 | `githooks/adapters/gate-8.sh` | `src/gates/gate-8.ts` | CLI |
| Gate 9 | `githooks/adapters/gate-9.sh` | `src/gates/gate-9.ts` | CLI |

TS 版的文件头自己写着：

> `TypeScript rewrite of githooks/adapters/gate-3.sh for cross-platform Node.js CLI.`

**「rewrite」意味着两份实现。** 两份实现意味着：

- 修了一边忘了另一边（#632 / #633 就是这个）
- 两边行为微微不等，没人发现（没有等价性测试）
- 新功能只加一边

### 2.2 三条执行路径，无人验证一致性

```
① git hook  → githooks/pre-commit      （用户仓库）
② npm CLI   → src/npm-package/bin      （命令行）
③ skill     → skills/*/SKILL.md        （Agent 会话）
```

**同一个项目，走这三条路可能得到不同结论，而没有任何测试检查这一点。**

这是比分层重要得多的不变量。`#652` 已经踩到一角：

> BUILD 阶段对门禁规则不可知：Boy Scout/CCN/jscpd/archlint 在 skills 中出现 0 次，
> **27% 的门禁失败本可避免**。

—— skill 那条路根本不知道自己会撞上什么门禁。

### 2.3 回归的根因收敛

638 个 issue 里，明确的回归复发 9 例。它们的根因几乎全落在上面两条：

| 模式 | 代表 issue |
|---|---|
| 修一边忘另一边 | #632, #633, #649, #658 |
| 工具缺失/配置不被消费 → 静默 PASS | #615, #575, #686, #619 |
| 平台差异（Windows 路径） | #633, #656, #661, #669, #735, #740 |

**这三类都不是「某个函数写错了」，是结构允许它们反复发生。**

## 3. 为什么「越跑越慢」也是结构性的

`#640` 实测：7.3 分钟里 80% 是进程冷启动。

本机实测补充（写 Gate 6 校验器时）：
- 单次 `awk` 启动 **0.4–0.8 秒**（MSYS2 fork 开销）
- 我的脚本算法部分 2.1 秒，墙钟 6.2 秒，**差额全是 fork**

结构原因：

1. **每道门禁独立进程、独立冷启动、独立配置加载** —— 加一道门禁就加一次冷启动，成本线性叠加，收益边际递减
2. **镜像同步本身要遍历 50 组文件** —— Gate MP 稳定 10–11 秒
3. **47 组镜像对，`git ls-files -s` 每个文件一次** —— 注释里写着「94 次 git spawn，每次 200–260ms」

**这不是优化问题，是「有多少个进程」的问题。** 性能任务的 O1–O7 方向对（全量改增量），但它们优化的是**每个进程内部**，没有减少**进程数量**。

## 4. 治理方向：从「加门禁」改成「减结构」

### 4.1 第一原则：让重复无处可藏，而不是检查有没有重复

现在的做法是**写一道门禁去检查镜像是否一致**（Gate MP，10–11 秒，47 组文件）。

更好的做法是**让镜像根本不存在**。

| 现状 | 目标 |
|---|---|
| `githooks/pre-commit` → 复制 3 份 | npm 打包时**构建产物**生成，不进 git |
| 47 组镜像对需要同步 | 0 组，因为只有一份源 |
| Gate MP 花 10 秒比对 | 不需要这道门禁 |

**这是把「检查重复」换成「消除重复」。** 难度在于 npm 包必须能独立安装——但那是 `prepack` 脚本的职责（`sync-package-content.js` 已经在做 skills 和 plugins 了），不是 git 仓库的职责。

> 这一条如果做成，**仓库直接从 22.9 万行降到 11.5 万行，Gate MP 消失，一批漂移类回归根因消失。**

### 4.2 第二原则：一个门禁只有一个实现

`src/gates/gate-N.ts` 与 `githooks/adapters/gate-N.sh` 双实现必须收敛：

- **要么** shell 成为唯一实现，CLI 去调 shell（需要保证 Windows 有 bash）
- **要么** TS 成为唯一实现，shell 去调 node（要求 node 一定存在）

考虑 XP-Gate 已经强制要求 node（`xp-gate` 本身就是 npm 包），**TS 为唯一实现更合理**。但这是一次大改，需要单独设计。

**过渡期至少要有等价性测试**：同一组输入，两个实现必须给出相同 verdict。今天这个测试不存在。

### 4.3 第三原则：不变量要可执行，不要写在文档里

现在「三条执行路径应一致」这条不变量**不存在于任何地方**——不在文档、不在代码、不在测试。

它应该变成：

```
契约测试：给定 fixture 项目 + 预期 verdict
         ↓
    分别走 hook / CLI / skill 三条路径
         ↓
    断言三者结论相同
```

这是**唯一能防止 `#652`（skill 不知道门禁规则）这类问题复发**的机制。

### 4.4 第四原则：门禁要能证明自己有效

这是前面讨论的 meta-gate，现在有更具体的形态：

**每道门禁必须有一个「必须被拦住」的 fixture。** 不是测试函数逻辑，是测试这道门禁在真实缺陷前会不会红。

`#728`（archlint 检测器恒返回 0）、`#615`（ratchet 缺失判 PASS）、`#575`（SKIP 不算不通过）
三个问题，**都能被这一个机制抓到**——因为它们都是「门禁声称在查，实际没查」。

## 5. 建议的执行顺序

按「根因消除量 / 风险」排序：

| 阶段 | 内容 | 消除什么 | 风险 |
|---|---|---|---|
| **P0** | 镜像改为构建产物（不进 git） | 49.8% 行数、Gate MP、一批漂移回归 | 中（打包流程要改） |
| **P1** | 三路径一致性契约测试 | #652 类问题、`#575` 类假绿 | 低（纯新增测试） |
| **P2** | 门禁有效性 fixture（meta-gate） | `#728`/`#615`/`#575` 三类 | 低（纯新增测试） |
| **P3** | 双实现收敛（TS 唯一） | `#632`/`#633` 类 | 高（大改） |
| **P4** | 进程合并（减少 fork 数） | 冷启动主导的耗时 | 中（要重构门禁编排） |

**P0 是唯一能在数量级上改变仓库的。** 其余都是质量改善。

## 6. 一个需要你判断的取舍

镜像不进 git 之后：

- ✅ 仓库小一半，漂移消失，Gate MP 消失
- ⚠️ `src/npm-package/` 在当前 `npm pack` 之外不可浏览（但发布时生成，无影响）
- ⚠️ 需要 `prepack` 正确生成，否则包会缺文件（`#658` 就是这类问题——它已经发生过一次）

**`#658` 的存在说明这条路有坑。** 但那个坑的根因是「漏了一个目录」，而不是「构建产物不可靠」——一个 `files` 字段的测试就能覆盖。

## 7. 与已完成工作的关系

- **Gate 6 分层校验器**（`feat/gate-6-layer-enforcement` 分支）：对**用户项目**有价值，对 XP-Gate 自身无价值（本仓库没有 `src/domain/` 等目录）。建议 `architecture.yaml` 移到 `docs/examples/`，别再暗示本仓库有分层。
- **性能任务 O1–O7**：方向对，但它们不改变本文档指出的结构问题。**P0 做完后，O3（Gate MP 提速）直接作废**，因为 Gate MP 不再需要。
- **WSL 迁移**：fork 开销会消失，但这只是让症状缓解——进程数量没变。

---

## 8. 结论

你说的「故障高发、性能持续恶化」不是两个问题，是**一个**：

> **XP-Gate 用「增加检查」来对抗「结构不健康」，而它自己对不健康的容忍度恰恰是最高的。**

它对用户项目执行「Boy Scout Rule」「重复代码检测」「架构分层」，而自己：
- 一半代码是复制品
- 同一逻辑多个实现
- 不变量只存在于人的记忆里

**治理的起点不是加更多门禁，是让 XP-Gate 先通过它自己要求别人通过的那些门禁。**
