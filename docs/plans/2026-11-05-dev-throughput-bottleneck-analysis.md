### 1.1 必须拆掉的两个假数据（沿用前作并复核）

1. **resume/落盘污染**：工具区间 >10 min 一律视为"调用发出后用户走开、结果很久才落盘"，封顶 10 min。3 天内有 **~90 次**这样的区间，若按原值累加会得到数百小时的假象。本报告所有数字均用封顶后口径。
2. **模型延迟必须以"步末→下一步首个调用"取**：第一版按 `result→下一条消息` 硬算，得到 **446 h（占 94%）** 的荒谬结论——因为它是"工具区间 + 走开时间 + 下一轮唤醒"之和。改口径后 **10.39 h（29%）**。**这一条是本次复核最重要的方法论修正**，前作 2.1 节的 `job_output 66.5h + pwsh 69.4h = 54%` 很可能同样被 resume 污染过。

### 2.3 门禁自身的真实成本 —— 它是健康的

`audit.jsonl`（3 天，剔除 epoch 脏值 0 条，>10 min 仅 4 条）：

| Gate | 次数 | 合计 | 均值 |
|---|---|---|---|
| gate-5 tests-coverage | 38 | 2,981 s | **78.5 s** |
| gate-10 sast-security | 7 | 781 s | 111.6 s |
| gate-3 complexity | 47 | 687 s | 14.6 s |
| gate-12 file-hygiene | 33 | 580 s | 17.6 s |
| gate-1 code-quality | 47 | 538 s | 11.4 s |
| 其余 9 个 gate | — | < 350 s each | ≤ 10 s |
| **合计** | **533** | **6,784 s = 1.88 h** | |

- 门禁执行 **533 次，失败 31 次（5.8%）**，构成：
  - **gate-12 file-hygiene 18 次**（机器可判、非业务缺陷）；
  - **`gate_id=unknown` 19 次**（`failure_reason: gate_exit_1`，即钩子以非 0 退出但**未能记录是哪个 gate**）；
  - **真实业务失败仅 1 次**（gate-11 sprint-flow，原因是 R1 共识未达标，见 §5）。

  也就是说：**当前返工压力的主体是"钩子挂了 / 文件规范不过"，不是"业务代码被门禁正确拦下"。** 这直接支撑 §4 —— 返工的成本发生在执行环节，而不是设计环节被拦下。
- `git commit` 完整电池：**中位 49 s / p75 94 s / p90 147 s**，105 次合计 2.09 h。
- `git push`：中位 58 s，40 次合计 0.50 h。

> **门禁直接成本**（gate 执行 1.88 h + commit 电池 2.12 h + push 电池 0.50 h）**≈ 4.5 h，占工具忙碌墙钟 25.77 h 的 17.6%**；其中纯 gate 执行仅 **7.4%**。前作"门禁提速一倍只省 4.3%"的结论今天依然成立——**所以提速门禁不是本轮的答案**。

## 3. 瓶颈 #1：BATS 门禁测试套件（6.51 h / 36%，且不可并行）

### 3.1 实测证据

| 实验 | 结果 |
|---|---|
| 单文件 `githooks/__tests__/gate9-architecture.test.bats` | **2 s** |
| 单文件 `githooks/__tests__/adapter-common.test.bats`（18 tests） | **21 s** |
| **两个文件一起跑** | **281 s** |
| 3 天内 bats 调用 | 213 次，合计 **6.51 h**，平均 **110 s** |
| 其中撞上 600 s 封顶 | 多次（`kotlin-gate.test.bats`、`issue-717-csharp-*`、`gate-13-*`、`issue-ccn-ratchet`） |
| 测试文件总数 | **213 个 `.bats`** |
| `setup()` 内是否有 sleep/install | **没有**（`adapter-common.test.bats` 的 setup 只 source 一个 shell 文件） |

### 3.2 机制

1. **全量 setup 成本与定向成本严重倒挂**：跑 1 个文件 21 s，跑 2 个文件 281 s。说明主力成本不是被测代码，而是 **bats 的逐用例 fork + shell 环境重建 + 上百个 `npx`/`node`/`tsx` 冷启动**。改一行 shell，想验证一个用例，必须先付这份成本。
2. **为了绕开这个成本，实践里演化出大量重复执行**：日志里同一组 `issue-717-csharp-*.bats` 被反复跑（`timeout 900`、`timeout 500`、`timeout 400` 各来一次），因为每次修改后只能整组重跑。
3. **它串在 `git commit` 里**：pre-commit 有 5,559 行、~13 个 gate，几乎全部串行（全文只有 1 处 `&`，且那是 audit 写日志）。**p90 147 s、最大 600 s** 的提交等待，其中大头就是这类 shell 集成测试。

### 3.3 把门禁提速一倍的收益 = 4.3%；把 BATS 提速一倍的收益 = 18%。这就是为什么本轮该动的是测试套件，不是 gate 阈值。

## 5. 瓶颈 #3：Delphi R1 空转 —— DESIGN 阶段 3.65 h

`.sprint-state/sprint-state.json`：

| 阶段 | 耗时 |
|---|---|
| Phase 1 PREP | **30 s** |
| **Phase 2 DESIGN** | **13,137 s = 3.65 h** |
| Phase 3 BUILD | 3,230 s = 0.90 h |
| Phase 4 VERIFY | 至今 `in_progress`（自 11-03 16:42 起已停滞 **> 45 h**） |

`phase-outputs/requirements-reviewed.json` 记录了 DESIGN 为什么会花 3.65 h：

```json
{ "consensus_percent": 33, "threshold_percent": 90,
  "rounds_run": 7, "rounds_limit": 5,
  "status": "PROCEEDED_WITH_DISSENT" }
```

- R1 跑 **7 轮**（**已超规范 5 轮上限**），共识停在 **33%（1/3）**，三条硬伤未闭合，最终由**用户人工裁决**推入 BUILD。
- 3 天内 `ask_user_question` **27 次、2.37 h**（平均 317 s/次），`Delphi/外部评审命令` **440 次、1.92 h**。
- **合规代价**：R1 证据文件自述"不得据此声称设计已获批准"，但 sprint 已进入 VERIFY。也就是说，这 3.65 h 里相当一部分是**为了满足一个达不到的门槛而反复重跑**，而不是澄清设计。

> 这是"开发慢"里唯一**非技术**的主因：流程设计了一个 90%/5 轮的双重硬约束，但实际共识能力给不出这个结果，于是每次设计都退化为"超轮次 → 人工裁决 → 留 dissent 记录"。**耗尽的是人的等待时间（ask_user_question 2.37 h），不是机器时间。**

## 8. 优化建议（按 ROI，每条带验收口径）

### P0 — 让 BATS 可定向（1 周，回收 ~3.3 h/3 天）

1. **拆分 `githooks/__tests__/` 的 setup 成本**：把 `setup()` 里可共享的 fixture 建到 `BATS_TEST_TMPDIR` 一次、跨用例复用；对仅做 `grep`/静态断言的用例（日志里存在大量"断言某行存在"的用例）**改成 vitest 的纯文本断言**——它们不需要起 shell。
   - **验收**：`adapter-common.test.bats` 从 21 s 降到 ≤8 s；单个 issue-717 文件 ≤60 s。
2. **给 bats 加"变更→文件"映射**：`scripts/bats-affected.sh` 依据 `git diff --name-only` 选择相关 `.bats`，pre-commit 只跑相关的，全量留给 pre-push / CI。
   - **验收**：改 `adapters/typescript.sh` 时 pre-commit 跑的 bats 文件数 <10。
3. **禁止无界重跑**：日志里同一组测试被 `timeout 900/500/400` 反复跑三次。改为单次运行 + 失败即读 `--print-output-on-failure` 定位。
   - **验收**：单次任务的同组 bats 执行次数 ≤2。

### P1 — 把红线前移到写代码前（落地前作 P1，回收 ~2.4 h/3 天 + 返工率）

4. **`xp-gate check --changed --brief`**（前作 P1-4，仍未实现）：只跑本次 diff 触发的 gate，≤15 行、**目标 <5 s**。
   - **验收**：本仓库中等改动上计时 <5 s；输出 gate→PASS/SKIP/BLOCK 一屏。
5. **`skills/sprint-flow/references/phase-3-build.md` 增加「提交前自检清单」**：CCN>5 warn/>10 block、Boy Scout（新文件 0 warning / 函数 ≤50 行 / 嵌套 ≤4）、jscpd >5%、mirror 纪律、Gate-12 会拦的冲突标记/YAML-JSON 语法。
   - **验收**：该文件出现上述全部阈值（当前 `skills/` 中 CCN/jscpd/archlint/mirror 出现 **0 次**，用 `grep` 可直接核对是否落地）。

### P2 — 修 Delphi 空转（需产品决策，回收 ~3.0 h/3 天）

6. **把"共识阈值"与"轮次上限"解耦**：
   - 选项 A：保留 90% 但取消 5 轮上限（允许 R 轮循环直到闭合）。
   - 选项 B（**推荐**）：把 R1 的通过条件从"90% 共识"改为"**零 unresolved 硬伤**"，因为本轮实测 7 轮后仍 33%，说明该门槛在本项目不可达，只会定期触发人工兜底。
   - **验收**：下一个 sprint 的 DESIGN 阶段耗时 ≤1.5 h（本轮 3.65 h），且 `requirements-reviewed.json` 中 `rounds_run ≤ 3`。
7. **`PROCEEDED_WITH_DISSENT` 必须阻断 phase-transition**（当 `evidence_schema_version≥2`）：当前它被写成 `status` 但未阻断，导致"设计未批准"的 sprint 一路走到 VERIFY 并停滞 45 h。
   - **验收**：`phase-transition` 对该 status 返回 `ok=false`。

### P3 — 收尾调用效率（回收 ~4.4 h/3 天）

8. **规则 2 真正执行**：calls/step 1.130 → 2.0。日志里存在大量"一次 shell 一条命令"的步骤；`AGENTS.md` 规则 2 已写但 `runtime-journal` 显示未执行。
   - **验收**：`xp-gate runtime-journal --days 3` 的 `calls/step ≥ 1.8`。
9. **规则 3 真正执行**：`job_output` 阻塞 5.40 h（138 次，均 141 s），字面 `sleep` 45 次，CI 轮询 78 次。
   - **验收**：`job_output` 阻塞 >30 s 的次数下降 ≥50%；CI 轮询改为完成通知。

## 11. 重大更正（2026-11-05，同日复核）—— BATS 不在 pre-commit 里

第 3 节原先断言"BATS 串在 `git commit` 里"，**这是错的**。核实证据：

```
$ grep -n 'bats' githooks/pre-commit
1398:    # marker); see githooks/__tests__/issue-527-subdir-multimodule.test.bats.
```

**pre-commit 对 bats 的唯一提及是一行注释**，从不执行它。真实位置是 **`npm test`**（`scripts/run-bats.cjs` 把它链在 vitest 之后）。按调用点重新归因：

| bats 调用点 | 次数 | 小时 |
|---|---|---|
| 独立执行（agent 手动/定向跑） | **353** | 6.4 |
| 包在 `git commit` 命令里 | 5 | 0.5 |
| **合计** | **358** | **6.92** |

### 11.1 随之作废的结论

- ❌ "BATS 是 pre-commit 门禁的一部分，撑出 p90 147 s 的提交等待" —— **作废**。`git commit` 那 2.12 h 里没有 bats。
- ❌ 我实测的 **"两个 bats 文件一起跑 281 s"** —— **作废**，那次读数受系统负载污染（当时并行跑着一轮超 600 s 的 vitest）。**负载干净时复测：单跑 `adapter-common` 29.9 s、单跑 `gate9` 2.8 s、两个一起跑 2.8 s** —— 完全没有超线性放大。**"setup 成本与用例数脱钩" 这个机制不成立。**
- ❌ P0-2 "给 pre-commit 加 bats 增量选择" —— **不适用**，因为 pre-commit 根本不跑 bats。

### 11.2 仍然成立的部分

- ✅ BATS 确实是**最大单项**：6.92 h / 3 天，占 shell 时间 ~38%。
- ✅ 但它**已经具备增量性**（定向单文件），它的问题是**执行纪律**：353 次独立调用里，只有约 **30 次是 `stryker`**，其余是同一个文件被反复重跑（日志里 `issue-701-*`、`issue-711-*` 各跑 2–3 次，`issue-717-csharp-*` 整组重跑 5+ 次，末尾还夹着一批 `/tmp/probe*.bats` 探针）。
- ✅ `adapter-common.test.bats` 的 18 个用例确实要 **30 s**（成本在每条用例 fork bash + 脚本内部再起子进程），迁 vitest 对"纯静态断言"类用例仍有收益 —— 但收益规模需要重新测，不是我原先估的 3.3 h。

### 11.3 结论方向的变化

原 P0（"让 BATS 可定向"）**降级**——它已经能定向。真正的 P0 变成两件事：
1. **执行纪律**：同一组 bats 文件在一次任务内的重跑次数上限，以及把"改一行 shell → 全组重跑"换成"只跑受影响的单文件"。
2. **确认谁在给 ×2.8 估值买单**：§2.2 的 vitest 2.29 h 是**未被截断**的低估值（全量 `vitest run` 本地跑 >600 s 超时）。
