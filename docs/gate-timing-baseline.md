## 二、这张表会骗人：它是双峰的

`gate-10` 的 p90 = 168 秒看起来是压倒性的瓶颈。但把它的记录按时间排序后：

```
> 60s 的记录：114 条 / 489
按月分布：2026-10: 56 条，2026-11: 58 条
最后一条 > 60s：2026-11-19T12:42:47Z
之后 33 条：中位 203ms，p90 263ms，最大 20000ms
```

**规则集缓存上线之后，p90 从 168021ms 降到 263ms，改善 638 倍。**

p90 被历史慢记录拉高，不代表当前状态。**一个只报 p90 的基线会让人去优化一个已经解决的问题。**

### gate-12 的测量教训

历史记录里 gate-12 稳定在 28-31 秒。我一开始据此认为它是第二大瓶颈。

但那是**矩阵 4 路并发时测出来的**。单独测量：

```
G12 第1次: 6604ms
G12 第2次: 5930ms
G12 第3次: 5865ms
```

**并发争用被误读成产品缺陷。** 这正是 `AGENTS.md` 的测量纪律第 5、6 条：
A-B-A 不够，ABBA 交替 + 记录每轮负载；负载差 >5% 的对比无效。

## 四、2026-11-23 复测：三个计时缺陷的修复与验证

本节记录这一轮针对"高效性"所做的修复，以及**每一条的测量证据**。
所有加速比都来自 ABBA 交替测量，且报告了每组负载。

### 4.1 gate-3：3.3 倍（15.4s → 4.7s）

ABBA 交替，低负载（loadavg 0.00，8 核），同一变更集
（`scripts/gate-timing-report.cjs` 单文件）：

| 臂 | 第 1 轮 | 第 2 轮 |
|---|---|---|
| old（0.38.104.0） | 15532 ms | 15222 ms |
| new（0.38.105.0 实现） | 4666 ms | 4748 ms |

组内方差 < 2%，交替消除了时间趋势。**加速比 3.3×**。

根因：population 过滤是逐行 `while read`，**每一行起一个 `awk` 进程**
（本机 awk 启动 ~211 ms）。85 行 CSV = 85 次进程启动 ≈ 18 s，
占了整条门禁 62% 的时间。改为**单次 awk 遍历**后消失。

### 4.2 一个必须先修的陷阱：优化落在了没人执行的那个副本里

上面 3.3× 的数字第一次**没有生效**。`githooks/gate-3.sh:374` 早写着：

> **THIS FILE HAS A TWIN.** ... **Any change here must land in BOTH.**

但 `gate-3-entry.sh` 执行的是 `source "$GATE_DIR/gate-3.sh"`，而优化只落在
`githooks/adapters/gate-3.sh`。`xp-gate doctor` 在本仓库报
`ADAPTER_DIR: D:\projects\xp-gate\githooks`，命中的正是没被优化的那份。

实测两个文件的差距：**14.4s vs 4.5s**。

**测试为什么没抓到**：`gate-3.test.bats` source 的是 `githooks/gate-3.sh`，
断言的是**判定正确**，而两个实现判定都对。**一个测"结果对不对"的测试，
抓不到"改了但没生效"。** 只有计时能抓到。

修复后两文件 md5 一致，真实提交里的 gate-3：

| 提交 | gate-3 耗时 |
|---|---|
| 修复前（`d0e22713`） | 61.3 s |
| 修复后（`75e65c69`） | **4.5 s** |

### 4.3 计时报告本身在误导：两条记录共享时钟

按判定分组后，`test-focus` 出现在耗时榜首（中位 44.4s），而它的代码注释写着
这项检查"应在毫秒内失败"。原因：它的 `record_gate_audit` 传的是 `GATE_5_START`
—— Gate 5 的起点，于是**记录的时长是 Gate 5 从开始到此刻的全部工作**。

这不只是显示问题：计时报告把每个 gate 的 `duration_ms` 当作互不重叠的成本求和，
两条记录报重叠时间会让"分钟花在哪"重复计数，且重叠那段被算给后记录的那个。
已改为各自取时钟。

### 4.4 一条没能证实、明确标注为"测不出来"的线索

`tests-coverage` 有 117 次以 `powershell: no Pester tests` 跳过，累计 79.6 分钟，
看起来是巨大的浪费。但直接单跑同场景只需 **216–536 ms**。

对照那次提交的其它 gate（`version-consistency` 24.6s、`code-quality` 23.6s，
均显著高于平时），判断是**整链资源争用**而非该门禁的缺陷——当时机器上还有
我自己的探针在跑。

**按六条规则第 6 条，这一条结论是"测不出来"，不是"已修复"，也不是"有问题"。**
低负载复测是下一步，不是现在就能下的判断。

### 4.6 怎么复现

```bash
node scripts/gate-timing-report.cjs          # 表一：按门禁；表二：按判定
node scripts/gate-timing-report.cjs --json   # 机器可读
```

判定分组表（`SPLIT BY VERDICT`）是本轮新增的：一个门禁一行中位数，
在它大部分时间跳过时**描述的是跳过路径**。gate-3 修复前的例子：
中位 1.0s、p90 59.1s、占比 0.9%——而它实际是全链最贵的门禁。

## 五、gate-1 的 20 秒花在哪（2026-11-23，负载 32%）

gate-1 中位 20.0s、占整链 21%，是第二大项，所以值得拆开看。

单次直接测量（同一台机器，负载 32%，各测一次；单次值用于定位量级，
不用于比较两个实现）：

| 环节 | 耗时 |
|---|---|
| `tsc --noEmit` | 7277 ms |
| `eslint src`（全量，JSON 输出） | 9113 ms |
| 其余（shellcheck、重复分析、编排） | ~3.6 s（由总时长反推） |

**结论：这一项不是缺陷，是真实工作量。**

- **没有重复分析**。AGENTS.md 里记载的陷阱是「adapter 定义
  `run_lint() { run_static_analysis; }`，导致同一份工作做两遍」。这里核对了：
  `eslint` 在 gate-1 里只被调用一次（154/156 行是**互斥分支**，不是顺序执行）。
- **没有和 gate-9 重复**。担心的第二处是 gate-9 也跑 `tsc`——核查后 gate-9
  只检查 `package.json`/`tsconfig.json` **是否存在**（第 219 行），不执行编译。
  所以那 7.3 秒只花了一次。
- **没有网络等待**。两者都是本地二进制，无 `npx` 解析。

按"高效性"的判据——单门禁 p90 耗时占比应与其价值相称——gate-1 检查的是
整个 TypeScript 代码库的类型正确性和 lint 规则，20 秒对应约 644 个源文件，
是相称的。

**这条写下来的意义在于：不是每个慢门禁都是缺陷。** 上一轮 gate-3 的
15.4 秒是缺陷（85 次进程启动、62% 的时间在等解释器启动），修完变成 4.7 秒。
gate-1 的 20 秒性质完全不同——**问"它在等什么"得到的是"它在编译"**。

两者外观一样（都很慢），结论相反。区分它们要靠拆解，不能靠排名。

## 六、gate-5：一个"跳过"花掉 20 秒，但我复现不出来（2026-11-23）

gate-5 是整链最大项（中位 20.4s，占 28%）。按判定分组看：

| 判定 | n | 中位 | p90 |
|---|---|---|---|
| PASS | 24 | 29.9 s | 160.7 s |
| SKIP | 126 | 20.7 s | 56.8 s |

PASS 比 SKIP 慢是合理的——真跑了测试才会 PASS。**问题在 SKIP 也有 20.7 秒。**

而 126 次 SKIP 里，明细只有两种：

| SKIP 明细 | n | 中位 |
|---|---|---|
| `powershell: no Pester tests` | 90 | **25.4 s** |
| `no_code_files_changed` | 36 | 8.1 s |

一个"这个项目没有 Pester 测试"的决定，中位花 25.4 秒。

### 我尝试复现，失败了

在隔离环境直接调用 `gate_5_run()`（补齐 `jscpd-run.sh`、`gate-5c-alignment.sh`
依赖，注入桩函数）：

```
gate_5_run: 4614 ms
```

**4.6 秒，不是 25 秒。** 而且仍有 1 个依赖缺失，说明真实路径比这更长——
也就是说 4.6 秒是下界，但它到达不了 25 秒。

排除过的可能：

- **不是同链争用**（六条规则第 5 条）。查了三次慢记录的同一分钟：
  `00:42` 那次 gate-5 花了 25.2 s，而同一分钟**其它门禁合计只有 9.0 s**。
  链上并不拥挤。
- **不是 `find` 慢**。SKIP 判定本身是一次 `find`（`*.Tests.ps1`），毫秒级。

### 结论：**测不出来**，不归因

按六条规则最后一条——宁可说"测不出来"，也不要给出方向错误的结论——
这一条留在这里。

已经能确定的：**25.4 秒不花在 SKIP 判定上**（那是毫秒级），也不花在同链争用上
（同分钟其它门禁合计仅 9 秒）。剩下的怀疑对象是 gate-5 在进入语言分支之前
的某个前置步骤，而它在隔离调用下不会执行。

**下一步**（留给下一轮，不要凭猜测改代码）：给真实钩子里的 gate-5 加时间戳打点，
分段输出到 stderr，跑一次真实的 docs-only 提交，看 25 秒落在哪一段。
这里写的是**尚未定位**，不是"已修复"。

## 七、结论

- **没有可测量的持续瓶颈。** 历史上最大的两个耗时源（gate-10 的网络规则集、
  gate-12 的并发争用）都已解决或证伪。
- **数据库本身的卫生是个真问题。** 2.4% 的记录是垃圾值，任何 consume audit 的
  工具都必须按 `duration_anomaly` 排除，否则结论会错几个数量级。
- **单次测量不可信。** 本机长期 80-100% CPU，同一门禁在并发与串行下相差 4-5 倍。

## 八、复现方法

```bash
# 有效样本统计（排除 anomaly 和 >2h）
node -e "const fs=require('fs');const MAXP=7200000;..." # 见 .timing.json

# 单个门禁计时（串行，避免并发争用）
s=$(date +%s%3N); XP_GATE_ONLY_GATE=12 git commit -m t --allow-empty; echo $(($(date +%s%3N)-s))ms
```

单门禁计时必须用 `git init -b probe<name>` 的临时仓库，
因为 `XP_GATE_ONLY_GATE` 在受保护分支（`master`/`main`）上会被拒绝。
