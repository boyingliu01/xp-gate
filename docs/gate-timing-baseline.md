## 二、这张表会骗人：它是双峰的

`gate-10` 的 p90 = 168 秒看起来是压倒性的瓶颈。但把它的记录按时间排序后：

```
> 60s 的记录：114 条 / 489
按月分布：2026-10: 56 条，2026-11: 58 条
最后一条 > 60s：2026-11-19T12:42:47Z
之后 33 条：中位 203ms，p90 263ms，最大 20000ms
```

**规则集缓存上线之后，p90 从 168021ms 降到 263ms，改善 638 倍。**

p90 被历史慢记录拉高，不代表当前状态。**一个只报 p90 的基线会让人去优化一个已经解决的问题。**

### gate-12 的测量教训

历史记录里 gate-12 稳定在 28-31 秒。我一开始据此认为它是第二大瓶颈。

但那是**矩阵 4 路并发时测出来的**。单独测量：

```
G12 第1次: 6604ms
G12 第2次: 5930ms
G12 第3次: 5865ms
```

**并发争用被误读成产品缺陷。** 这正是 `AGENTS.md` 的测量纪律第 5、6 条：
A-B-A 不够，ABBA 交替 + 记录每轮负载；负载差 >5% 的对比无效。

## 四、结论

- **没有可测量的持续瓶颈。** 历史上最大的两个耗时源（gate-10 的网络规则集、
  gate-12 的并发争用）都已解决或证伪。
- **数据库本身的卫生是个真问题。** 2.4% 的记录是垃圾值，任何 consume audit 的
  工具都必须按 `duration_anomaly` 排除，否则结论会错几个数量级。
- **单次测量不可信。** 本机长期 80-100% CPU，同一门禁在并发与串行下相差 4-5 倍。

## 五、复现方法

```bash
# 有效样本统计（排除 anomaly 和 >2h）
node -e "const fs=require('fs');const MAXP=7200000;..." # 见 .timing.json

# 单个门禁计时（串行，避免并发争用）
s=$(date +%s%3N); XP_GATE_ONLY_GATE=12 git commit -m t --allow-empty; echo $(($(date +%s%3N)-s))ms
```

单门禁计时必须用 `git init -b probe<name>` 的临时仓库，
因为 `XP_GATE_ONLY_GATE` 在受保护分支（`master`/`main`）上会被拒绝。
